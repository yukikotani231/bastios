# BastiOS architecture

How the kernel is put together, and which part of it is proved. Read the [README](../README.md) first for what BastiOS does and how to build it. The language the kernel is written in is described in bastiolang's [language reference](https://github.com/yukikotani231/bastiolang/blob/main/docs/language.md); the capability types below (`Pool`, `Frame`, `PageTable`, `Mmu`, `Cpu`, `Serial`) are explained in its "Kernel capabilities" section.

## The big picture

```text
            proved (Bastio)                          trusted (C, assembly)
  +--------------------------------------+   +----------------------------------+
  | user/*.bastio   sh, hello, spin, ... |   | user/start.S   image header,     |
  |   (--target user, ring 3)            |   |                calls main, exits |
  +------------------|-------------------+   +----------------------------------+
                     | int 0x80 / timer / fault
  +------------------v-------------------+   +----------------------------------+
  | src/main.bastio     scheduler loop   |<->| boot/boot.S    multiboot, long    |
  | src/syscall.bastio  system calls     |   |                mode, trap stubs, |
  | src/proc.bastio     processes        |   |                bst_cpu_enter     |
  | src/fs.bastio       open files       |   |                                  |
  | src/pcache.bastio   shared file pages|   |                                  |
  | src/ramfs.bastio    in-memory files  |   |                                  |
  | src/diskfs.bastio   files on disk    |   |                                  |
  | src/blk.bastio      disk: USB stick, |   |                                  |
  |   NVMe, virtio, AHCI or ATA (xhci,   |   |                                  |
  |   nvme, virtio_blk, ahci, ata.bastio)|   |                                  |
  | src/net.bastio      IPv4 stack over  |   |                                  |
  |   card.bastio: virtio_net or e1000   |   |                                  |
  | src/virtq.bastio    virtqueues, and  |   |                                  |
  |   pci.bastio                         |   |                                  |
  | src/space.bastio    address spaces   |   | boot/platform.c  TSS, IDT, PIC,  |

  |                                      |   |   COM1, arena, PTE encoding, CR3 |
```

**Devices.** Drivers are Bastio and reach hardware only through capabilities claimed once in `main`: I/O ports (`PortIo`: serial, PIC, PIT, PCI configuration, ATA, virtio), memory-mapped registers (`Mmio`: the HPET, the framebuffer, an xHCI controller, an NVMe drive, an e1000 card and an HD Audio controller, in the device window `boot.S` maps uncached: 2-4 GiB with 2 MiB pages, then up to 2^46 with 1 GiB pages, where firmware puts 64-bit BARs) and pages lent to devices for DMA (`Dma`). Both virtio drivers share `src/virtq.bastio` (the legacy register block and the virtqueue). The disk is a virtio block device when the machine has one: `src/virtio_blk.bastio` lends it five pages (the virtqueue, one request, and a data page for 4 KiB blocks) at boot, programs their physical addresses into the device, and takes them back only after resetting it at power off. While they are lent the prover rejects any attempt to free, map or reuse them, and every access to them is volatile and inside the page. That the device writes only those pages, and stops when reset, is trusted. An NVMe drive comes first when there is one (`src/nvme.bastio`): its BAR, 32- or 64-bit, is claimed as an `Mmio` once it is checked to lie in the device window clear of the framebuffer, and five pages are lent as `Dma` (the admin and I/O submission and completion queues, 64 entries each, and one data page). The driver disables the controller, sets up the admin queue, reads the size and block size of the first active namespace (namespace 1 on almost every drive; the active namespace list says which) (512 bytes or 4 KiB; the driver counts 512-byte sectors either way, so on a 4 KiB drive one sector is read as its whole block and written by reading, patching and writing back the block), and creates one I/O queue pair without interrupts. Each read or write is one command, for one sector or for one 4 KiB file system block, through the data page, waited for by polling the completion queue's phase bit; a write is followed by a flush, so it is on the medium when it returns. At power off the controller is shut down (which writes back its cache) and disabled before the pages come back. Register, queue and page accesses are proved in bounds; that the controller writes only the lent pages is trusted. Without NVMe or virtio, a SATA disk on an AHCI controller is used (`src/ahci.bastio`): its BAR 5 is claimed as an `Mmio`, and two pages are lent, one holding the command list, the received-FIS area and the command table, the other the data. The driver takes the controller from the firmware (BIOS/OS handoff), sets AHCI mode, and walks the implemented ports: each gets its spin-up bit (for controllers with staggered spin-up) and, if its link is down, a COMRESET (every port with a device does with the boot option `ahci_reset`). The first port whose link is up with a disk's signature, or with no signature yet, is stopped, pointed at the pages and given FIS receiving; a device that then reports another signature (a CD) is let go and the walk goes on. The disk's port is started. IDENTIFY gives the size (a disk whose sectors are longer than 512 bytes is not used: QEMU cannot emulate one on AHCI, so that path could not be tested); each read or write is one READ/WRITE DMA EXT in command slot 0, for one sector or eight, with one PRD entry, polled until the slot clears, and a write is followed by FLUSH CACHE EXT. At power off the port is stopped before the pages come back. Without any of these the disk is the ATA drive, driven by programmed I/O. A USB stick or disk comes before all of them (`src/xhci.bastio`, on the same controller as the USB keyboard, which is therefore set up first): the first device with a SCSI mass-storage interface over the bulk-only transport, on a root port or behind hubs (see Console), gets a slot of its own and its two bulk endpoints. Each SCSI command is a 31-byte command block wrapper on the OUT endpoint, the data, and a 13-byte status wrapper on the IN endpoint; the status wrapper is asked for only once incoming data has arrived, since a device may not accept the request while it is still sending (QEMU's does not). After INQUIRY, TEST UNIT READY (retried, with REQUEST SENSE, while the device is not ready) and READ CAPACITY (512-byte sectors only), the driver reads the GPT and uses the stick only if it has a partition of the BastiOS type, e0c9ea2a-d5f1-45b3-a799-0a7bec83d701, and then only that partition: `make usb` builds a stick image with the ISO's Limine and kernel before it (`tools/mkusb.py`). A stick the user booted from is the disk they chose, so the machine's own disks are then not touched at all; a stick without the partition is never written. Reads and writes are READ(10) and WRITE(10) through the data page, and a flush is SYNCHRONIZE CACHE, which a stick that does not know the command answers with a check condition and is then taken to write through. An error (a stall, or a status wrapper that is not the command's) gets the transport's reset recovery: both endpoints reset and stopped with their queues skipped, a mass-storage reset, and both halts cleared. When the controller has MSI-X with its table in BAR 0, interrupter 0 raises `V_DISK` for every event (no moderation), as the other DMA disks do, so a process waiting for the stick sleeps: a read takes two interrupts (the data, then the status wrapper the first one asked for), a write or flush one. Without MSI-X the disk is polled. The event ring is shared with the keyboard, so a key also raises `V_DISK` while the stick is the disk; the poll that follows takes it. That the device's status is true is trusted, as with the other disks. Every driver finds its device by walking PCI configuration space through the legacy ports: every bus the firmware numbered, every slot, and the other functions of multi-function devices.

**Console.** The console (`Con`, `src/console.bastio`) is COM1 plus, when there is one, a screen and a keyboard. Output goes to both; input is taken from the serial port first, then the keyboard. The screen (`src/fb.bastio`) is the linear framebuffer the boot loader set up: the kernel's Multiboot header asks for 1024x768 at 32 bits per pixel, Limine sets it through VBE under BIOS or GOP under UEFI, and the `boot_fb` builtin hands the kernel what Limine reported. If it is 32-bit RGB and lies in the device window, below the I/O APIC (under QEMU it is at 0xFD000000 under BIOS and at 2 GiB under UEFI, which is why the window starts there) or above 4 GiB on a processor with 1 GiB pages (many PCs put the graphics memory there, at 0x4000000000 on recent Intel ones; `boot_fb` reports only framebuffers below 4 GiB, so `main` reads it through `boot_info`, and this case is untested: no QEMU display has its framebuffer above 4 GiB), the kernel claims it as an `Mmio` and draws text in 8x16 cells: an 8x8 public-domain font doubled vertically. Every pixel write is proved inside the claimed block. The text is kept in a byte buffer with a copy of what each cell shows, so scrolling redraws only the cells that change; ANSI escape sequences are skipped. Booted with `-kernel`, QEMU sets no video mode and the console is serial only. The keyboard (`src/kbd.bastio`) is a PS/2 keyboard on the i8042, polled through its two ports (unless the status port reads 0xFF at boot: no controller, as on many recent PCs): scan code set 1 becomes the bytes a terminal would send (Enter is CR, Backspace DEL, Ctrl-C 3), with Shift and Ctrl tracked; other extended keys are dropped. A PS/2 mouse on the controller's second port is turned on at start (the aux port enabled, then the mouse's defaults, the IntelliMouse sequence that turns on a wheel if it has one, and data reporting, each acknowledged), and its bytes, which arrive on the same data port marked by the status register, are put together into 3-byte packets, or 4-byte ones with the wheel; a byte that cannot start a packet (bit 3 clear) is dropped, so a lost byte costs one packet and the stream falls back into step. `pump` hands whole packets to the kernel with the typed bytes (`exchange`), into a 192-packet ring that Linux programs read as `/dev/input/mice` or `/dev/psaux` (`src/lxmouse.bastio`), in the PS/2 format Linux's mousedev gives by default, or in ImPS/2 with the wheel once a program asks for it. Like the keyboard, the mouse is polled, so on hardware a burst can overrun the controller's one-byte buffer between polls; that costs packets, not the stream. A USB mouse feeds the same ring (below). A USB keyboard works too (`src/xhci.bastio`): the first xHCI controller on PCI gets its registers claimed as an `Mmio` (the BAR, sized the usual way, in the device window and clear of the framebuffer) and fifteen pages lent as `Dma` (the slot array, the command ring, the event ring and its segment table, the device contexts of five slots, the input context, the control rings of the five slots, the keyboard's and the mouse's interrupt transfer rings, four scratchpad pages, and the USB disk's bulk rings and data page). The driver takes the controller from the firmware (USB legacy support), resets and starts it, and attaches the first device that offers a HID boot keyboard interface, on a root port or behind USB 2 hubs: a slot, an address, the configuration, the boot protocol, and its interrupt IN endpoint, on which one 8-byte transfer is always queued. Each finished one is a boot report, and keys newly down become the same bytes as on PS/2. The first device with a HID boot mouse interface becomes the mouse the same way; its boot reports (buttons, then signed x and y motion, down positive, then on most mice the wheel, up positive) are turned into PS/2 packets (y up positive) with an ImPS/2 wheel byte (up negative), dropping reports in which nothing changed, and reach `/dev/input/mice` by the path the PS/2 mouse's take. A wireless receiver that offers both interfaces on one device is both, on one slot with two interrupt endpoints. It is polled with the other inputs, or, when the controller has become the disk (see Devices), through the disk under the kernel lock, in the step of `pump` that hands typed bytes to the kernel; one event ring serves every device, and whichever is waiting takes the others' events for them; at power off the controller is reset and the pages come back. Every register and page access is proved in bounds; what the controller writes into the lent pages is read defensively (descriptor lengths are bounded, unknown events skipped) but trusted to stay in them. Hubs are followed two tiers deep, which is five slots at most (two hubs, the keyboard, the mouse and the stick): a hub gets a slot, is configured as one (its port count, and its transaction translator's think time if it is high speed), has its ports powered, and each port with a device on it is reset and the device attached, with a route string naming the ports on the way and, for a low- or full-speed device behind a high-speed hub, that hub's slot and port as its transaction translator. A hub nothing was taken under gives its slot back. Hub requests wait by the controller's microframe counter. A USB 3 hub is seen only through the USB 2 hub inside it, so a SuperSpeed device behind one is not found (QEMU has no USB 3 hub to test with). That the boot loader reports the framebuffer truthfully is trusted.

**Network.** A virtio network card, when present, gets nine pages the same way (two virtqueues, four 2 KiB receive buffers, one transmit page). Without one, an Intel card of the e1000 families (`src/e1000.bastio`) is driven instead: the 8254x most hypervisors and many older PCs offer (82540EM, 82544GC, 82545EM), the 82574L, and the igb family (82576, I350, I210, I211), which shares the register layout but keeps queue 0 at 0xC000 and 0xE000, enables it on its own, takes only advanced descriptors under QEMU (whose write-back puts the status where the legacy one has the length, and overwrites the buffer address, which is given again with each buffer), and negotiates the link only when its PHY is told to through MDIC. QEMU has the 8254x models, the 82574L (`e1000e`) and the 82576 (`igb`), and all are tested; the I350, I210 and I211 are not. The I217-I219 and I225/I226 are different designs and have no driver. Its 128 KiB register block is claimed from the device window as an `Mmio` once its BAR is checked to lie in the window below the I/O APIC. It gets six pages: both descriptor rings, eight 2 KiB receive buffers and one transmit page. Both drivers are polled, and both can also signal a received frame (see "Waiting for the network" below). `src/card.bastio` puts the two drivers behind one `Card` type. `src/net.bastio` is a minimal IPv4 stack on it. Its address, netmask and gateway come from a DHCP client that starts when the card does (DISCOVER, OFFER, REQUEST, ACK; retried on the timer, no lease renewal), falling back to QEMU's user-mode defaults (10.0.2.15/24, gateway 10.0.2.2) if no server answers four tries; the shell's `ifconfig` shows them (system call 47). The stack speaks Ethernet, ARP (it answers requests for its address and keeps a four-entry cache), IPv4 without options or fragments (header checksum checked on the way in), ICMP echo both ways, and UDP with checksums sent and checked. Every field is read out of a byte buffer, and the proof shows no length read off the wire can take a read or write outside it: a header claiming more bytes than arrived is dropped. The card (`Nic`) lives in the `Kernel` struct, inside the shared `Sys` state, and each processor's scheduler polls it under the lock on every pass. Nothing in the stack waits, so no network wait holds the lock: a frame whose next hop has no cached MAC is held (one at a time) and sent when the ARP answer arrives, and a ping (system call 40) puts its process in the `NETWAIT` state until `net_wake`, run on every scheduler pass, finds the reply or the two-second deadline. On top sits a table of eight UDP sockets (`sock_new`, `sock_bind`, `sock_sendto`, `sock_recvfrom`, `sock_ready`, `sock_peer_ip`/`sock_peer_port`, `sock_port`, `sock_close`), each queueing up to four datagrams (later arrivals are dropped, which UDP allows); unbound sockets get an ephemeral port (49152 and up) on their first send, and `sock_recvfrom` never waits: blocking belongs to the caller. A port no socket has falls back to the echo service on 7. The shell reaches sockets through native system calls 41-46 (`udpecho`, `udpsend`). `src/tcp.bastio` adds TCP: a table of `TCBS` connections, each with a receive and a send ring of `TCP_RING` bytes (256 KiB), opened by listening (`tcp_listen`, `tcp_accept`) or connecting (`tcp_connect`, then `tcp_status`), with `tcp_send`, `tcp_recv` (0 at the end, `TCP_AGAIN` when nothing has arrived) and `tcp_close`, none of which waits. A ring is a level-1 page table that holds only the pages its data is in (`src/tcpbuf.bastio`): a page is taken when data first goes in it and given back once everything in it has been read or acknowledged, so an idle connection holds no data pages. The network code runs without the page allocator, so it takes pages from a table of spare pages that the kernel tops up before each poll of the card and in each TCP system call (`nic_feed`), and gives back what is over a high-water mark; together they stay within an eighth of the pool. A ring that finds no spare page takes what fits and the peer resends the rest. Data that arrives early is held in the receive ring at its place (one stretch of it per connection) and joins once the gap before it is filled. Unacknowledged data is resent go-back-N; the timeout starts at one second and doubles on each resend, up to 64 seconds, and the connection is reset after eight unanswered resends. Segments keep to the MSS the peer asked for, or 536 bytes if it didn't say. A zero window is probed with one byte for as long as the peer keeps answering. Window scaling (RFC 7323) is on when the peer's SYN offers it, so the window can cover the whole ring. When the peer takes SACK blocks (RFC 2018), an ACK sent while data is held past a gap names that stretch, so a sender that reads them resends only the gap; BastiOS's own sender does not read SACK blocks (it resends go-back-N) and has no congestion control. `test/tcp_test.sh` checks these paths, which QEMU's user-mode network never takes. It joins the card to the script through QEMU's `dgram` netdev, and the script plays the network: ARP, DHCP, and a TCP peer that drops, delays, reorders and duplicates segments, by rule or on a seed (`SEED=n`). The shell reaches TCP through native system calls 48-55 (`tcpecho`, `tcpget`). A packet for this machine (127.0.0.0/8, its own address, or 0.0.0.0 as a destination) never reaches the wire: `send_via` puts it on a loopback queue of `LOQ` frames (TCP stops a burst rather than overflow it, and leaves out its checksum there, as Linux does on `lo`), and `net_poll` takes in what was queued when it started, as if it had arrived, before reading the card. A packet to 127.x carries 127.x as its source, so both ends of a loopback connection agree on the addresses. Loopback needs a network card, since the stack exists only with one. IPv6 (`src/net6.bastio`) is translated rather than built beside it: a UDP datagram or TCP segment that arrives over IPv6 for one of our addresses (link-local, or the advertised prefix with the EUI-64 interface id from the card's MAC) is checked, rewritten in the receive buffer into the IPv4 packet it stands for, from a token in 240.0.0.0/8 that names the peer's slot in a 16-entry table of (address, MAC), and handed to `ip_in`; a frame the stack builds for a token is rewritten into IPv6 by `v6_out` as it leaves `send_via` or `reply_send`. Both directions move the transport header by 20 bytes and recompute its checksum over the other pseudo-header, so `src/tcp.bastio` and the UDP sockets never see an IPv6 address. ICMPv6 is answered in `src/net6.bastio` itself: neighbor solicitations and advertisements (a frame for a neighbor with no known MAC is held, as for ARP), router solicitations at start and the prefix and router from the advertisement, and echo. `test/ipv6_test.sh` plays a router and hosts on the card's wire, as `test/tcp_test.sh` does, because QEMU's user network needs IPv6 on the host. Linux AF_UNIX stream sockets (`src/lxunix.bastio`) do not use the stack: socketpair, and bind, listen, connect and accept on a name, join two descriptions through a pair of 4 KiB one-way channels of their own. A name lives in one of four slots until its socket closes. A path name is resolved from the working directory, and bind makes a socket file there whose mode says who may connect (see [security.md](security.md)); a name in the abstract namespace (a leading 0 byte) makes no file and is compared byte for byte.

**Sound.** An Intel High Definition Audio controller (every PC since 2004; QEMU's `intel-hda` or `ich9-intel-hda` with `hda-output` or `hda-duplex`) plays through `/dev/dsp` (`src/hda.bastio`, `src/lxsnd.bastio`). Its BAR is claimed as an `Mmio` once it is checked to lie in the device window clear of the framebuffer, the USB controller and the disk, and six pages are lent as `Dma`: the command rings (the CORB, 256 commands, and the RIRB, 256 answers, in one page), a buffer descriptor list, and four data pages. The driver resets the controller, starts the rings, and walks the first codec's audio function group: every output pin that is wired up (its configuration default does not say "no connection") as line out, speaker or headphones gets a path back to a DAC, straight from the pin or through one or two mixers or selectors; every node on the path is powered, its amplifiers (only those it has) set to 0 dB unmuted, its selector pointed along the path, and each DAC told to take stream 1 as 48 kHz 16-bit stereo. QEMU's controller sends no more commands after RINTCNT answers until the RIRB's answer flag is cleared, so the flag is enabled (with the controller's interrupt still off) and cleared before each command. Stream 1, the first output stream, plays the four pages in a loop: a 16 KiB ring, about 85 ms. It is polled, not interrupt-driven: on every tick of the bootstrap processor `snd_poll` reads how far the controller has played (LPIB), zeroes what was played, so nothing plays twice if the writer falls behind, and counts it off what is queued; after half a second of silence the stream stops, and the next write starts it again at the top of the ring. A `write` queues what fits behind what is queued and returns that count; a write to a full queue waits (`lx_retry`). The OSS ioctls that set the rate, channels or format answer with the one format played, as OSS lets a driver do; `SNDCTL_DSP_SYNC` returns at once rather than waiting for the queue to drain. There is no mixer device, no recording, and no other format, so a program that wants 44.1 kHz must resample. Without a sound card, `/dev/dsp` fails to open with ENODEV. Register, ring and page accesses are proved in bounds; that the controller reads only the lent pages is trusted. `test/shell_test.sh` boots with QEMU's `wav` audio backend and checks the file it writes: `mtone`'s half second of a 1 kHz square wave, 1000 half periods of exactly 24 frames, nothing lost or played twice.

**ACPI.** `src/acpi.bastio` does what a PC needs from ACPI beyond finding its processors: soft power off, restart, the power button, and a clock where there is no HPET. The firmware's tables are read through the `boot_acpi` builtin, a byte at a time (`boot/smp.c` finds them: any table the XSDT or RSDT lists, and the DSDT through the FADT), and parsed in Bastio, every read checked against the table's end. From the FADT it takes the PM1a event and control blocks, the PM timer (24 or 32 bits), the SMI command port and the reset register; the only AML it reads is the DSDT's `\_S5` package, found by name (a NameOp, `_S5_`, a PackageOp, its length and count, then a ByteConst, Zero or One), not by interpreting the DSDT. The three register blocks sit together in one I/O block on every chipset (QEMU 0x600, Intel 0x400 or 0x1800, AMD 0x800), which `acpi_new` claims as one `PortIo` before any other port, if it is no longer than 256 ports and clear of the ports the kernel claims by number and the PCI configuration ports; the PCI drivers then keep their I/O BARs off it (`blk_find`, `nic_new`). PM1b blocks, which QEMU does not have, are not driven. Firmware still in legacy mode is switched to ACPI mode through the SMI command port, so that the power button reaches the kernel; its status bit is enabled and then polled on every tick of the bootstrap processor rather than taken as an SCI (IRQ 9 stays masked), and a press powers off as `halt` does. `halt` (and `poweroff -f`, through Linux's reboot(2)) ends with the S5 sleep type and SLP_EN written to PM1a control, after the isa-debug-exit port the tests use. `reboot` (and `reboot -f`) writes the FADT's reset register when it is a port the kernel holds (QEMU's and most chipsets' 0xCF9, in the PCI configuration ports), or a memory register in the chipset part of the device window (0xFEC00000 to 4 GiB, where no PCI BAR goes), which `main` claims as a one-byte `Mmio` at boot, before the HPET and the local APIC, if it is clear of both (no QEMU machine has one, so this path is untested), then pulses the keyboard controller's reset line, then writes 0xCF9 itself. The HPET is taken from where the ACPI HPET table says; without one (`-machine hpet=off`) the clock is the PM timer, extended to 64 bits on every read, which every tick makes often enough. The local APIC timer the application processors use is calibrated in `boot/smp.c` against the same: the HPET, else the PM timer, else PIT channel 2, else one second of the RTC (between two of its updates; slow, but every PC has one). With neither the HPET nor a PM timer, which many recent PCs turn off, `boot/smp.c` measures the time-stamp counter's rate in the same window, and the clock runs on that rate. When PIT channel 0 does not count (Intel's "8254 clock gating"), the bootstrap processor's 10 ms tick comes from its local APIC timer on the same vector. The processors come from the MADT's local APIC and x2APIC entries alike. The local APICs run in xAPIC mode, which `src/lapic.bastio` drives through its page of registers; a firmware that left them in x2APIC mode (SeaBIOS and OVMF do on machines that may have ids of 255 or more, and many PCs with VT-d) has that undone in `smp.c`, since x2APIC registers are MSRs, which Bastio cannot reach. Only when the firmware locked x2APIC mode, or a processor has an id xAPIC cannot address, does `smp.c` keep x2APIC mode, and the kernel then does without MSI and `V_WAKE` (polled disks, and parked processors looking for work on their timer tick). QEMU emulates x2APIC without KVM from 9.0, so these tests need `QEMU_X2APIC`. `test/shell_test.sh` checks all of it on QEMU's i440fx and q35 machines, without isa-debug-exit and without `-no-reboot`, so only the kernel's ACPI code can end QEMU. The tables may lie anywhere the kernel's page tables map: `boot/smp.c` walks them before each read. `boot.S` maps the second GiB for this alone (firmware puts the tables at the top of the memory below 4 GiB, which on a machine with 2 GiB or more is there; the test boots a q35 with 2 GiB), and above 4 GiB they are reachable with 1 GiB pages.

**The hardware report.** With the boot option `diag` (the second entry of the ISO's Limine menu, or `-append diag` under QEMU's own loader), `main` prints what it found, a screenful at a time, waiting for a key (or a minute) after each so that the screen can be photographed: lines for what the boot log does not mention (no screen, no USB keyboard, no disk, no network card), then `src/info.bastio`'s parts: the processor (CPUID's vendor, name, family and the features that matter), how many processors the MADT lists and how many run (and if not all, why), what the local APIC timer was calibrated against and the clock; the memory map; where the RSDP came from, every ACPI table with its address, the ACPI registers the kernel drives; and every PCI function with its ids, its class and what BastiOS does with it. The facts only the platform has (the command line, the memory map, CPUID, what processor startup saw) come from the `boot_info` builtin, which promises nothing about its answers: each is checked before use like any other input. [real-hardware.md](real-hardware.md) says what to send back.

The Bastio compiler turns each Bastio file into freestanding C, after proving it. The C is compiled and linked with the trusted parts into one kernel image, and each user program into a flat image that the kernel embeds. The boundary between the two columns is the set of capability builtins: Bastio code never sees an address it could dereference, only linear values (`Frame`, `PageTable`, ...) that the builtins turn into memory accesses.

## Booting

1. QEMU loads `build/bastios.elf` with its Multiboot 1 loader. (The kernel is linked as 64-bit code and repackaged as ELF32, because that loader accepts only 32-bit images.) From `build/bastios.iso` (`make iso`), Limine loads the same file with Multiboot 2, under BIOS or UEFI (`boot/limine.conf`): the kernel carries both headers. Multiboot 2 also passes a copy of the ACPI RSDP, which UEFI firmware gives only to EFI programs. Once in long mode, `boot/multiboot.c` copies the Multiboot 2 fields the kernel uses (memory map, framebuffer, RSDP) into the kernel image, in the Multiboot 1 form, so everything after it reads one format.
2. `boot/boot.S` starts in 32-bit protected mode, identity-maps the first 1 GiB with 2 MiB pages (kernel-only: no user bit), turns on long mode with write protection, and loads a GDT with kernel and user segments.
3. `bst_platform_init` (`boot/platform.c`) fills in the TSS (the stack a trap from ring 3 lands on), the interrupt table (vector `0x80` is raisable from ring 3; #DB, NMI, #DF and #MC switch to a 4 KiB IST stack in the processor's block, because the first instructions of the `syscall` entry run in ring 0 on the user's stack), the two 8259 interrupt controllers, and a 100 Hz timer.
4. `bst_smp_init` (`boot/smp.c`) starts the other processors. It finds them in the ACPI MADT (every firmware read checked against the table's length and the identity map or the device window), reached from the RSDP: the copy Multiboot 2 passed, else where BIOS firmware puts it, finds the local APIC (inside the device window boot.S maps uncached), copies the trampoline in `boot/ap.S` to physical `0x8000`, and sends each application processor INIT and startup IPIs, one at a time. The processor climbs from real mode to long mode on the kernel's own page tables, loads the kernel's GDT and IDT, counts itself in, and parks with interrupts off, waking on its local APIC timer to look for work. `cpu_count` tells the kernel how many processors are up, and the shell's `cpus` command shows it. The kernel hands every parked processor the scheduler with `smp_run` (`bst_platform_smp_start` / `bst_platform_smp_join` in `boot/smp.c`), see "The scheduler loop".
5. `bst_kmain` (the kernel prelude, generated by bastiolang) initialises COM1, builds the `Pool` from the Multiboot memory map (every run of available RAM above the end of the kernel image, up to 512 GiB, with page numbers running on across the holes between runs; without a map, from the memory size; `boot/multiboot.c` first maps the RAM above 2 GiB write-back and tells the prelude how far the map reaches) and calls the Bastio `main` with the four capabilities it is entitled to: `&mut Serial`, `&mut Pool`, `&mut Mmu`, `&mut Cpu`.
6. When `main` returns, `boot.S` writes to QEMU's debug-exit port and the machine powers off.

## Memory

**Physical pages.** `src/pages.bastio` keeps a `Mem`: the `Pool` capability together with a bitmap of free pages (one 8-byte entry per page of the pool, however much RAM there is; at least `LOW_PAGES`, since drivers take fixed pages below that), and a hint `low` below which no page is free. The spec `mem_ok` says the bitmap agrees with the pool (`get(bm, i) == 1` exactly when `pool_has(pool, i)`), and every function that touches `Mem` must preserve it. Since `pool_take` demands `pool_has`, and `take_page` demands the bitmap bit, a page is never handed out twice. That is proved, not tested. `count_free` at power off is how the test checks that nothing leaked.

**Virtual memory.** Every top-level (level-4) table has two parts:

| Slot | Maps | Owner |
| --- | --- | --- |
| 0 | The kernel: the boot identity map of the first 512 GiB (RAM write-back, the device window uncached), without the user bit | Not owned; `pt_new` points it at the kernel's own map in every new level-4 table, and the prover rejects any `pt_put` or `pt_take` on slot 0 |
| 1 | The process's user window: `WPAGES` = 2^27 pages (512 GiB) from `USER_BASE` = `0x8000000000` | The process, through one level-3 table, up to `WIN_L2S` = 512 level-2 tables and up to `WIN_L1S` = 512 level-1 tables under each, each made when a page under it is first mapped; loops over a range of the window skip the tables that are not there (`w_next`) |

The program image starts at page 0 of the window and the stack takes the top `STACK_PAGES` pages. Nothing else is mapped at the start: a Linux program's heap (`brk`) grows up from the image and its `mmap` pages come down from the stack, each page mapped when asked for. `mmap` takes an address hint when nothing is there (`mmap_hint`, `src/lxmem.bastio`), as the Go runtime wants for its heap at `0xc000000000`. Private writable anonymous `mmap` memory, and the heap `brk` adds, is only recorded at first (`src/lxanon.bastio`): a page fault in it maps a fresh zero page, as on Linux, so a program can reserve more than the machine has and pay for what it touches; the kernel's own copies to and from user memory (`src/usermem.bastio`) map such a page the same way. `fork` of a process with one thread copies no page: each private writable page becomes a shared page marked copy-on-write, read-only in both processes, and the first write from either side gives that side its own copy (`src/lxcow.bastio`). A process breaks every such page before it starts a second thread, since a page can only be taken out of a table no processor is running on. `new_space` (`src/space.bastio`) builds this from the bottom up, taking every page from `Mem`; if memory runs out half way, it frees what it built and returns `Space::Empty`, so a failed spawn leaks nothing. `free_space` tears it down level by level; `pt_free` and `pt_free_root` require an empty table, so the proof shows every page is returned, and `pt_free_root` also requires that the table is not the one in CR3.

**Kernel heap.** `Buf`, `Vec` and `Box` values in the kernel come from the prelude's fixed 8 MiB arena, not from the page pool. Running out of it halts the machine (see "Limits").

**Reading user memory.** The kernel cannot dereference a user pointer. To copy a user buffer (`write`, `spawn`'s program name), it takes the level-3 and level-2 tables out of their parents, then for each page takes its level-1 table out of the level-2 one and the page out of that (`w_read`, `w_write` and `w_byte` in `src/space.bastio`), reads or writes the bytes it needs on that page, and puts everything back. Ownership is moved, never aliased, so the proof covers these copies too. `user_range` checks first that the buffer lies inside the window; a page that is not mapped ends the copy early.

## Processes

`src/proc.bastio` holds the kernel's state in one struct:

```text
struct Kernel {
  mem: Mem,             // the page allocator
  spaces: Vec[Space],   // element pid is that process's address space
  procs: Buf,           // the process table: a row of STRIDE words per pid
  q: Buf,               // console input waiting for a read
  ticks: u64,           // timer ticks since boot
}
```

The spec `kok(k)` (allocator consistent, one `Space` per pid with every mapped space a level-4 table, table and queue the right sizes) is a precondition and postcondition of everything that takes the kernel. `Mmu` and `Cpu` stay with `main` and are lent where needed.

A process is a row of the table, indexed by pid (1 to `NPROC - 1`; pid 0 means "none"). The row holds the state, the parent, the program, a tick count, a wait target or exit code, and the 18 saved user registers in `cpu_get` order. Address spaces live in `spaces`, outside the table, because a `PageTable` is linear and a `Buf` row can only hold numbers. Code that needs a process's space takes it out with `take_space` (which leaves `Space::Empty` behind) and puts it back with `put_space`. While it is out, nothing else can reach it.

The table, and the per-process tables that go with it (`sigact`, `cwd`, `croot`, `sigsave`, the Linux descriptors `lxfd` and the file layer's open-file rows `ftab`), start with 32 rows and double when a new process finds every row taken (`new_pid`), up to `NPROC` (256). Doubling and not a fixed step, because the kernel's allocator reuses a freed block only for a buffer of exactly the same size: each table a growth leaves behind stays unused. A row past the end reads as all zeros, a `FREE` process, and a write to one changes nothing, so code indexed by any pid below `NPROC` stays safe without knowing how long the tables are; `new_pid` hands out only ids the tables have rows for. A table that cannot grow because memory ran out makes `fork` fail with `EAGAIN`. (At 64 MiB of RAM the tables stop at 128 rows; at 256 MiB they reach 256.) Pipes (512 at most) take a 4 KiB ring when they are opened, double it up to 64 KiB only as they fill, and give it back when both ends are closed, so an idle pipe costs a page, as on Linux.

States: `FREE`, `READY`, `READING` (blocked on console input), `WAITING` (blocked on a child), `ZOMBIE` (exited; its code is held for the parent), `RUNNING` (on a processor, with its space and FPU page taken out), `KILLED` (killed while `RUNNING`: it ends when its processor brings it back), `NETWAIT` (waiting for a ping's reply), `CONWAIT` (writing to the console while its output ring is full; the call restarts once the ring is half empty). `spawn` builds the address space first and claims a row only if that succeeded. `terminate` frees the space, hands the exit code to a waiting parent, and orphans the children.

Programs are not loaded from disk: `prog_image` returns each program's flat image with `include_bytes`, and `spawn` checks its header (magic `BSTUSER\n`, memory size, entry point inside the image) before mapping it. Only the image bytes are known at compile time, so the header is checked at run time like any untrusted input.

## The scheduler loop

Every processor runs the same loop, `sched` (`src/main.bastio`), started on all of them at once by `smp_run(sched, ..)`. Each passes its own `Cpu` and `Mmu`; what they share is one `Lock[Sys]` holding the kernel's state (`Kernel`), the console's output ring (`Con`), the interrupt controllers (the 8259 pair and the bootstrap processor's local APIC) and the HPET clock, and a separate `Lock[Term]` for the console's devices (serial port, screen, keyboard). The lock's invariant, `kok(k) && con_ok(con) && pic_ok(pic) && lapic_ok(apic) && hpet_ok(clock) && acpi_ok(acpi)` (the ACPI block holds the power button and, without an HPET, the clock), is what a processor may assume when it takes the lock and must restore before it lets go; the prover checks both (bastiolang `docs/language.md`, "Locks and struct invariants"). Kernel code runs with interrupts off, so a processor never takes an interrupt while it holds the lock.

1. With the lock (`next_job`): after an interrupt or an idle wait (not after a system call), poll the network card and hand typed input to processes blocked in `READ` (`wake_readers`); then pick the next `READY` process after this processor's last one, round robin (`pick`). If there is none: stop if no process is alive, else wait for an interrupt without the lock (`cpu_idle`). Otherwise take its FPU page out, load its registers into this processor's `Cpu`, load its address space into CR3 with a lease (`mmu_enter`), and mark it `RUNNING`, so no other processor picks it. The address space stays in the table: threads of the same process run on other processors at the same time, each with its own lease (see "Threads on several processors" below).
2. Without the lock: load the FPU state, enter user mode until the next trap (`cpu_run`), then switch back to the kernel's map, give the lease back (`mmu_exit`) and save the FPU state. A few system calls are answered right here, without the lock, and the task runs on (`fast_call`): `getpid`, `gettid`, the user and group ids, and `sched_yield` while no other process is `READY` (a flag `turn` and `next_job_p` publish under the lock). They need nothing but the registers and what the processor learned when it took the task. Whatever they skip (a pending signal, a kill, tick accounting) waits for the task's next other trap, at the latest its timer interrupt. `clock_gettime` does not trap at all: Linux programs read the monotonic and real-time clocks through the vDSO (`user/vdso.c`), a read-only page the kernel maps just below the stack and names in `AT_SYSINFO_EHDR`. The kernel keeps time with the time-stamp counter, its rate measured against the HPET at boot (`src/tsc.bastio`), and copies the clock's parameters into that page, so the vDSO and `k.ns` read one clock with the same arithmetic.
3. With the lock (`finish`): put the FPU page back, bring the thread group's shared state to this thread (`group_take`), save the registers, error code and fault address into its row, and act on the trap vector:
   - `32` (the PIT, on the bootstrap processor) or `48` (each other processor's local APIC timer): count the tick and move on to the next process. This is the preemption.
   - `0x80` (system call): handle it (`syscall`); it says whether to keep running the same process, switch, or power off.
   - `0x31` (`V_DISK`, a disk command finished), `0x32` (`V_WAKE`, another processor woke a process) or `0x33` (`V_NET`, the virtio network card received a frame): nothing beyond the device poll of the next step 1. They are acknowledged at the local APIC here, under the lock (`src/lapic.bastio`). An e1000's interrupt comes through the 8259 like the timer's and is acknowledged the same way; the poll reads the card's interrupt cause, which lowers its line.
   - below `32` (an exception): print the fault and kill the process with exit code `128 + vector`. The kernel itself is unaffected.

   Step 3 and the next step 1 are one critical section (`turn`), so a system call costs one round trip of the lock.
4. Without `Lock[Sys]`, and before step 3 or step 1 (never while this processor holds a lease), if the console has output waiting (an `Atomic` count every critical section publishes) or an interrupt just came in: pump the console (`try_pump`). Kernel code never drives the console's devices; it appends to the 64 KiB output ring in `Sys`. One processor at a time pumps: it takes an `Atomic[bool]` with compare-and-swap, and the others skip instead of waiting. The pumper takes `Lock[Term]` and moves up to 16 chunks of 256 bytes. For each chunk it reads what was typed, takes `Lock[Sys]` just long enough to queue that input and take the next chunk of output (`exchange`), then writes the chunk to the serial port and the screen with `Lock[Sys]` free. The two locks only ever nest in the order `Term`, then `Sys`, which bastiolang's lock-order check (`E-LOCK-ORDER`) confirms. A `write` that does not fit in the ring blocks in `CONWAIT` and restarts once `exchange` has freed half the ring, so no byte is dropped. An idle processor pumps instead of sleeping while output is waiting and no other processor is pumping.

`kill` of a process that is `RUNNING` on another processor only marks it `KILLED`; that processor ends it in step 3. Power off sets a flag that every processor sees the next time it takes the lock, and `smp_run` returns once all of them have left the loop, so every space is back in the table. Then `main` takes the state out of the lock (`lock_end`), pops every remaining space and frees it, and prints the free page count, which `test/shell_test.sh` compares with the count at boot.

### Threads on several processors

The threads of one Linux process (`src/lxthread.bastio`) share one address space, and run on several processors at once: each processor running one holds a `Lease` on the shared top-level table (bastiolang `docs/language.md`, "Address spaces shared between processors"). The table stays in the `Kernel`'s table of spaces, where system calls on any processor use it. The rule that makes this safe is proved: while a tree has leases nothing is taken out of it, only added. System calls that read, write or map user memory (`src/space.bastio`, `src/usermem.bastio`) reach the lower tables and pages with `pt_borrow` instead of unlinking them, and a new page appears to the other threads as soon as its entry is written. Unmapping (`munmap`, `mprotect`, `mremap`, `mmap` with `MAP_FIXED`) waits until no processor runs the space: the caller is retried while its sibling threads are kept off the processors (`F_QUIET`), so no TLB shootdown is needed.

A space is freed only with no lease on it: `free_space` reads the run-time count (`pt_lease_count`) and waits for 0. In practice it never waits, because the scheduler frees a group's space only once none of its threads is on a processor: ending a group marks every running member `KILLED`, no new member starts while one is `KILLED`, and the group ends when the last of them comes back. `execve` in a group marks the other running threads `EXITING` and runs again until they have come back and been freed. The wait cannot hang: a processor holding a lease never waits for a lock (it pumps the console only before `turn` or `next_job`), and gives the lease back at its next trap, at the latest its next timer tick.

`make threadbench` (`test/threadbench.sh`) runs `mthread par`, four threads of pure computation (30 million xorshift steps each), on one processor and on four. Measured 2026-10-10 under QEMU with multi-threaded TCG on a 4-core host shared with other work, in milliseconds as the program reports them, two runs each:

| | one processor | four processors |
| --- | --- | --- |
| before (a group ran on one processor at a time) | 474, 472 | 499, 458 |
| after (leases) | 471, 491 | 236, 201 |

So the four threads now run about twice as fast on four processors. QEMU's processor threads share the host's cores with each other and with other jobs, so the ideal 4x is not reached here.

### How it scales

`make smpbench` (`test/smpbench.sh`) runs N copies of `bench` at once, on one processor and on four. The numbers below are wall seconds, measured 2026-10-10 under QEMU 8.2 with multi-threaded TCG (no KVM) on a 4-core host:

| | `-smp 1`, 4 copies | `-smp 4`, 4 copies | `-smp 4`, 1 copy |
| --- | --- | --- | --- |
| console devices written under `Lock[Sys]` (before) | 8.7 | 48.0 | 5.2 |
| console ring, pumped outside the lock (now) | 8.1 | 17.0 | 3.1 |

One copy on one processor takes about 2 s either way. I found where the time went by changing one thing at a time:

- **Almost all of it was the serial console.** `bench` writes 1 MiB to the console per copy, and each byte is two port accesses. With those writes made no-ops, the old kernel ran the four copies in 3.4 s on one processor and 4.4 s on four. Under single-threaded TCG (`-accel tcg,thread=single`, which emulates every processor on one host thread) it took 7.8 s and 8.9 s. So the kernel's own work scaled, and QEMU's cost of the UART did not.
- **QEMU serializes port I/O, and `pause` contends with it.** In multi-threaded TCG, every port access takes QEMU's global lock. So does every `pause` a processor executes: the instruction leaves the translated code, and QEMU takes that lock again before it re-enters. The old kernel held `Lock[Sys]` across its UART writes, so the other processors spun on that lock with `pause` and fought the writer for QEMU's lock. Even one copy on four processors ran at about a third of the UART speed of one processor. With the other three processors never started, it ran at full speed.
- **Every fix is also right on real hardware.** On a real 115200-baud line, holding the kernel lock for a 256-byte write stops every processor for 22 ms. The changes:
  - The devices are now written outside `Lock[Sys]`, by one processor at a time, and the others never wait for them.
  - A full ring blocks the writer instead of having it retry.
  - An idle processor sleeps instead of spinning while another one pumps.
  - Devices are no longer polled on every system call.
  - A system call takes the lock once instead of twice.

What is left is mostly emulation:
- `pause` still costs. As an experiment (not a change, because `pause` is the right instruction on real hardware), removing it from the spin loop cuts getpid on four copies from about 190 ticks to about 85, against about 130 on one processor.
- QEMU's four processor threads and its I/O thread share the host's four cores.
- A writer woken when the ring drains waits up to one 10 ms tick for an idle processor to pick it up: BastiOS sends no wake-up interrupts between processors. Measured and rejected (2026-10-10): sending one to each idle processor (claimed as an `Mmio` block of the local APIC) left 4 x `bench` unchanged within noise and made a single `bench`'s spawn+exit half as fast (49 to 94 ticks), because the child of a spawning parent then starts on another processor instead of on the parent's when it blocks in wait4. Waking only for writers, or with affinity, may still pay off; it needs a benchmark that shows it. The wake-ups BastiOS does send are `V_WAKE`, when a disk completion wakes a process while some processor is idle (see "Waiting for the disk without stopping the machine"), and the same on the bootstrap processor's tick while a process is left ready (see "Idle processors" below).

These numbers should be taken again on KVM or real hardware before `Lock[Sys]` is split further.

### Idle processors

A processor with nothing to run halts (`hlt`, in `bst_cpu_halt`) until an interrupt. The bootstrap processor ticks every 10 ms whatever it does: the tick keeps time, fires alarms and timers, and polls the power button and the devices that raise no interrupt. The other processors' 10 ms timers only preempt what they run and make an idle one look for work, and an idle one has nothing to preempt. So while one idles its timer is one-shot and a second long, a backstop (`bst_cpu_wait`, `boot/smp.c`), and the kernel wakes it with `V_WAKE` when there is work: when a disk completion wakes a process, and when a process is still ready after the bootstrap processor's tick (`next_job`, the `ticked` flag in `Sys`). That is when the idle processors' own ticks would have found it, so the scheduling is the same as before, 10 ms at worst; only the idle wake-ups are gone. At power off the processor that sees the stop first wakes the idle ones, so they leave at once rather than after their backstop. `V_WAKE` goes to every other processor, parked ones too (one not yet in the scheduler when `smp_run` starts, or one that already left it at power off); the park loop in `boot/smp.c` acknowledges it there. Before, a `V_WAKE` taken while parked stayed in service, and since it shares a priority class with the local timer (0x30-0x3F), that processor never took another timer interrupt or `V_WAKE`: it slept for good once idle. It was rare while `V_WAKE` came only from disk completions, and the new wake-ups made it show (`make test`: a spinning process not spread, `halt` hanging). Where the kernel cannot send `V_WAKE` (the local APICs in x2APIC mode) every timer keeps ticking. The hardware report (`diag`) says which.

Measured 2026-10-11 under QEMU 8.2 TCG on a shared 4-core host, the host CPU an idle guest at the shell prompt takes, in percent of one core over 20 s (`-m 256M`, a virtio disk):

| | `-smp 1` | `-smp 4` | `-smp 8` |
| --- | --- | --- | --- |
| every processor ticking (before) | 3.6 | 7.3 | - |
| idle application processors untimed (now) | 3.3 | 3.6 | 3.6 |

`make smpbench` and `make threadbench` are unchanged within noise (one `bench` on four processors: spawn+exit 51 ticks before and after; four copies 12.3 and 13.0 s before, 11.9 and 12.7 s after; `mthread par` on four processors 191 and 199 ms before, 248 and 184 ms after, while on one processor, which this does not touch, it varied as much, 402 to 485 ms). On hardware the gain is that an idle processor stays halted, and in the deeper C-states the chipset promotes `hlt` to, instead of waking 100 times a second.

Left as they are, and why:
- **`mwait` instead of `hlt`.** On hardware `mwait` can ask for a deeper C-state than `hlt`'s C1, but which hints a processor accepts comes from the DSDT's `_CST` objects (AML the kernel does not interpret) or from per-model tables, and in C3 and deeper the local APIC timer stops on processors without ARAT (CPUID 6, EAX bit 2). Under QEMU's TCG with more than one processor `mwait` is a `pause` (`helper_mwait` in QEMU's `target/i386/tcg/sysemu/misc_helper.c`), so an idle loop built on it would spin at 100% of a host core, and none of it could be tested here.
- **A tickless bootstrap processor.** Its tick does the polling above; it can stop only once every device the kernel polls raises an interrupt instead, and alarms program a one-shot timer.
- **S3 (suspend to RAM).** QEMU supports it on both machines by default (the DSDT has `\_S3`, and SLP_TYP 1 suspends), and wakes by resetting the machine with RAM kept, after which SeaBIOS jumps to the FACS's waking vector in real mode. So suspend is feasible, but resume means rebuilding the whole machine state the reset threw away: a real-mode waking vector that restores long mode, the descriptor tables, the TSS, the `syscall` and GS MSRs (trusted base, next to `boot/ap.S`); parking the application processors first and starting them again; the 8259, local APIC, PIT and HPET; the clock (the TSC and PM timer restart from 0); every PCI device's configuration (BARs, MSI); and each driver's queues (virtio, NVMe, AHCI, xHCI, e1000) after draining its commands. The plan, if it is wanted: a `suspend` command on one processor with the serial console only, then the processors, then each driver, with `suspend` refusing while any device lacks a resume path.

## System calls

A user program raises `int 0x80` with the call number in `rax` and arguments in `rdi`, `rsi`, `rdx`; the result comes back in `rax`. The numbers are the ones in bastiolang's user prelude, which provides the `sys_*` builtins:

| Number | Call | Effect |
| --- | --- | --- |
| 0 | exit(code) | Terminate the caller |
| 1 | write(va, n) | Write user bytes to the console; returns the count |
| 2 | read() | One byte of console input, blocking |
| 3 | spawn(va, n) | Start the program whose name is the user bytes; returns the pid or 0 |
| 4 | wait(pid) | Wait for a child and return its exit code |
| 5 | yield() | Give up the CPU |
| 6 | getpid() | The caller's pid |
| 7 | info(k) | 0: free pages; 1: ticks since boot; 2: processors running |
| 8 | ps() | Print the process table |
| 9 | kill(pid) | Terminate a process with code 137 |
| 10 | poweroff() | Stop the machine |
| 11 | open(flags, va, n) | Open the file named by the user bytes; flags `O_READ` 1, `O_WRITE` 2, `O_CREATE` 4, `O_TRUNC` 8, `O_APPEND` 16; returns a descriptor (0 to 7) |
| 12 | close(fd) | Close a descriptor |
| 13 | fread(fd, va, n) | Read up to n bytes (at most 4096) at the descriptor's offset into user memory; returns the count, 0 at the end |
| 14 | fwrite(fd, va, n) | Write up to n user bytes (at most 4096); returns the count |
| 15 | unlink(_, va, n) | Remove a file that no descriptor has open |
| 16 | dirent(i, va, n) | Copy the name of directory entry i; returns its length, 0 for an unused entry |
| 17 | seek(fd, off) | Move a descriptor's offset |
| 18 | stat(_, va, n) | The size of a file |

Calls 0 to 10 have named builtins in bastiolang's user prelude. The file calls (11 to 18) do not: user programs make them with the generic `sys_call(n, a, b)`, `sys_send(n, a, buf, len)` (lends the kernel bytes of a buffer to read) and `sys_recv(n, a, buf)` (lends a buffer to overwrite), wrapped in `user/lib/file.bastio`. A failed call returns `u64::MAX`.

Every argument is an untrusted number. The handlers check ranges at run time (`user_range`, pid bounds, states), and the proof makes sure no check is missing: a handler that indexed the process table with an unchecked pid would not compile.

`test/fuzz_test.sh` (`make fuzz`, and a short run in `make test`) checks this from the outside. `user/sysfuzz.c`, a freestanding program, makes random calls through both entry points (`syscall` with Linux numbers and `int 0x80` with native ones) with hostile arguments: kernel, device and non-canonical addresses, pointers at the edges of the user window and running off mapped pages, huge and negative lengths, bad descriptors. Several run at once on several processors. The kernel must not fault or stop answering, and every page must be back at power off. Most calls go to the Linux calls the kernel implements, all of them, and some to any number. It first opens a pseudo-terminal pair, a pipe, a socket pair and other descriptors for the calls to hit. Calls that would only end or stall the fuzzer itself (exit, signals to other processes, a read with nothing to read, a wait with no timeout, an armed timer) are left out or tamed with a zero timeout or a nonblocking flag; execve runs in a child, on programs that end at once. `test/sysfuzz_calls.sh` checks that every call the kernel dispatches is aimed at. A seed replays the same calls.

## Files

The file system is in memory (`src/ramfs.bastio`). Its directory is a flat table of 32 nodes, each free or one file: a name, a size, and a vector of pages, where page i holds bytes 4096 i to 4096 (i + 1). A page the file has never written is a hole and reads as zeros. The pages are `Frame`s taken from the page allocator, so a file owns its pages the way a page table owns the pages it maps: the proof shows that truncating or removing a file gives every page back once, and power off frees every file before counting the free pages.

`src/fs.bastio` sits between the system calls and the file system. It owns the open-file table (8 rows per process; a descriptor is a row number, so a process can only name its own files) and a 4096-byte transfer buffer. Each transfer is two copies: user memory to the buffer and the buffer to the file, or back (`src/usermem.bastio` walks the user window as the console `write` does). The file system below only ever sees the buffer. Each open row records which file system its file is on, and the few functions that touch a file dispatch on it; the system calls above do not know there are two.

Names that start with `disk/` are on the disk (`src/diskfs.bastio`), which keeps files across power off. The disk is cut into 4096-byte blocks: block 0 holds the magic `BSTDISK3`, blocks 1 to 4 the first 64 entries of the directory (256 bytes each), and the rest holds file data, the maps that find it, and the rest of the directory: up to 60 more blocks of 16 entries, each named in the superblock, added in order when the directory is full (the new block is written, zeroed, before the superblock names it) and never taken away, for 1023 entries in all (entry 64 is never used: its number means the top directory). An entry holds its kind, its parent entry, one path component of up to 200 bytes, a size, a mode, a modification time, and its root map: a block of 512 block numbers, each naming a first-level map of 512 data blocks, so a file can reach 1 GiB as far as the disk allows. Block number 0 is a hole and reads as zeros. Which blocks are free is not stored: mounting walks every file's maps and rebuilds the table in memory. The directory is kept in memory and written through. A `BSTDISK2` disk (the same with only the first 64 entries) is mounted as it is and its magic rewritten. A blank disk is formatted when it is mounted at boot. A disk with neither magic that is not blank (its first or last 34 sectors not all zeros: an MBR or GPT partition table, GPT's backup copy, a boot sector, another file system, or the first format, which had fixed 1 MiB slots) belongs to someone else: it is left alone, not a byte written, and the boot log says so. On a real machine that is the disk with its owner's system on it. Without a disk, names under `disk/` cannot be opened and everything else works.

The same disk file system can also sit on a disk image: an in-memory file formatted by `mkfs.bstdisk3` (`user/mkfs.c`) and mounted with `mount -t bstdisk3 IMAGE DIR` on an empty in-memory directory, IMAGE being the file or a loop device bound to it (`/dev/loopN`, `src/lxloop.bastio`; with no offset or size limit). While mounted, the loop device's bytes cannot be read or written and it cannot be unbound or reconfigured (`EBUSY`). The file layer keeps a second `DiskFs` for it (`v.lo` in `src/fs.bastio`); names below that directory go to it, and its entries get file handles of their own, after the disk's. Its driver (`src/loopblk.bastio`) is the image's pages: at mount the file hands them over, every hole filled with a zeroed page so a write never needs the page allocator, and commands finish at once, as ATA's do; at unmount the pages go back to the file. Meanwhile the image file cannot be opened for writing (`EBUSY`), and removing its name defers freeing it to the unmount. An image with no file system is refused (`EINVAL`) rather than formatted. One image is mounted at a time.

Names are paths, and both file systems hold directories as well as files: a directory is a node with no data, and what is in it is every node whose name starts with its name and a `/`. A file or directory can only be created while its parent directory exists, and a directory can only be removed while nothing is in it, so a file's parent always exists. A file removed while it is open loses its name at once and its data at the last close (`vfs_close`); on the disk it becomes an orphan entry (kind 3) in the meantime, and mounting frees any orphan a power cut left. `disk` itself is the disk's top directory and not a node. In memory a node's name is its whole path; on the disk an entry names only its last component and points at its parent, so a path is walked from the top. The kernel side is `vfs_mkdir`, `vfs_rmdir`, `vfs_dir_lookup` and `vfs_readdir(handle, index)` in `src/fs.bastio`; user programs reach them through calls 19 to 21, and the shell has `mkdir`, `rmdir` and `ls DIR`. A path can be up to 255 bytes. Each file and directory keeps permission bits and a modification time (`vfs_meta`, `vfs_set_meta`); writes, creation and truncation set the time from the kernel's clock, which counts from boot, as Linux `CLOCK_REALTIME` does here. `vfs_rename` (call 22, the shell's `mv`) renames a file or directory within one file system, never onto a name that exists or into itself; descriptors stay open on the file. On the disk it rewrites one entry, one sector, so a power cut leaves the old name or the new one; in memory a directory's contents are renamed with it. A symbolic link is a file whose mode carries the link type bits (`0xA000`) and whose contents are its target (`vfs_symlink`, `vfs_is_link`); the Linux layer follows links in every path it reads (`src/lxlink.bastio`), after `.` and `..` are taken out, so `link/..` is the link's own directory, not its target's parent. A hard link (`vfs_link`) is a node of its own that names a file: in memory a node whose `link` field holds the file's node, on the disk an entry of kind 4 whose field at byte 48 holds the file's entry. Opening or looking up the link gives the file (`vfs_target`), so descriptors, sizes and metadata are the file's, and `vfs_nlink` counts the links naming it. Removing a link removes only its node; removing the file's own name while a link remains moves the file onto that link's name and drops the link, so the file keeps its node and every other link still names it. On the disk the file's entry takes the link's parent and name in one sector write, which is the commit, and the link entry is cleared after (in the same write when the two share a sector); a power cut between them leaves the link naming its file under the file's own new name, and the mount drops such a link, as it drops one whose file is gone (`disk_take_name`). A rename from one name of a file to another name of the same file does nothing, as on Linux. A named pipe is a file too, with the FIFO type bits (`0x1000`, `vfs_mkfifo`, `vfs_is_fifo`); the Linux layer opens it as a pipe and keeps which pipe belongs to which FIFO in four slots keyed by the file's handle, so only the open FIFOs take a slot. `vfs_truncate` (call 23) sets an open file's length: bytes past a file's end are always zeros and blocks wholly past it are holes, so growing only moves the end, and shrinking zeroes the tail of the last block kept and drops the rest (on the disk by copying that block, its map and the root, then switching the entry, as a write does).

A power cut cannot leave the disk file system inconsistent, and it cannot tear a write. Data is never written over in place: a write builds the blocks it changes in memory, writes them and new copies of the maps above them to free blocks, flushes the drive's cache, and then switches the file to the new root and size by writing its directory entry (an entry never straddles a sector, so the entry's sector is written whole or not at all, and the rest of its directory block is rewritten unchanged). The old blocks are freed only after a second flush; removing and truncating write only the entry. ATA, AHCI and NVMe flush the drive's cache on request, and the virtio disk is write-through because the driver does not accept the cache feature. A write call returns to its process only once its last flush has finished. So a mount after a cut sees each write call entirely or not at all, even one that overwrites the middle of a file across a block boundary. Work that takes several calls (`O_TRUNC` and then writes) can still be cut between them. There is no journal because nothing else needs one. On a drive with 4 KiB sectors an entry's sector is written as its whole 4 KiB block, the others rewritten unchanged; NVMe makes a one-block write atomic across a power cut. `test/shell_test.sh` cuts power fifteen times during `user/crashme.bastio`, three times each on ATA, virtio, NVMe, AHCI and NVMe with 4 KiB sectors, and checks the files after each boot: a log must hold whole records, a snapshot file must be empty or whole, a region rewritten in place by single 4000-byte writes must never mix two of them, a file cut and regrown by `ftruncate` must read zeros past its cut, a file renamed back and forth must have exactly one of its two names, and a file linked and unlinked in turn (native call 24, `SYS_LINK`) must keep at least one name and its contents. Before each boot, `test/fsck.py` checks the image itself, as a mount reads it: entry kinds, names (no two alike in a directory), parents (no cycles), block maps (every block on the disk, none used twice, none wholly past a file's end, zeros after the end in the last block) and hard links. It reports orphans and dangling links, which the next mount clears, without failing. `test/fsck_test.py` damages images in each of those ways to show that fsck catches them, and the shell test boots one with the state a cut inside `disk_take_name` leaves to show the mount clears it.

Killing QEMU only cuts power between two completed writes, in order. A drive with a volatile write cache can do worse: it can lose any of the writes since the last flush, in any combination, and tear a multi-sector write (NVMe promises only one logical block is atomic). `test/crashsim.py` tests that. It runs `user/crashme.bastio` twice from a blank disk on NVMe behind QEMU's `blklogwrites` driver, which logs every write and flush the drive sees, and then rebuilds, without QEMU, every disk image a cut could leave: everything up to some flush plus every subset of the writes after it, and the same with one of those writes torn (its first half, its second half, a random mix of its sectors). Each image goes through `test/fsck.py` and a copy of crashme's checks that reads the files out of the image the way a mount would; a sample of them is then booted on virtio and checked by crashme itself, and so are a few of any failures, to show the kernel sees them too. Removing the flush between a write's new maps and its directory entry makes thousands of those images fail, and crashme fails on them when booted. `make crashsim` runs the whole thing (about ten minutes); `make test` runs a pass over every eighth flush.

**Waiting for the disk without stopping the machine** (`src/diskq.bastio`; the plan is [docs/design/async-disk.md](design/async-disk.md)).
- Reads and writes of file data go through a cache of 64 blocks and a queue of disk commands. The queue runs one command at a time, in order, and a flush in it is a barrier.
- A read whose blocks are all cached copies them out at once. Otherwise it queues reads of what is missing, plus up to eight blocks after it, and its process sleeps in `DISKWAIT`. Its call restarts once the queue has moved. Nothing changed before it slept, so restarting is harmless.
- A write first needs the old maps and the data it keeps in the cache, and it sleeps and restarts the same way until they are. Then, without waiting, it puts its new blocks in the cache (readers see them at once) and queues them: data and maps, a flush, its directory block, a flush, the release of the old blocks, and the end of the transaction. Its process sleeps, with its result already in `rax`, until that end is reached.
- The queue is moved along whenever the kernel polls devices. Every DMA disk says when a command has finished with a message-signalled interrupt, `V_DISK`, aimed at the bootstrap processor's local APIC: MSI-X on NVMe, virtio and a USB stick's xHCI controller, MSI on AHCI. So a processor with nothing to run halts, and the interrupt ends either its wait or the process it was running, which leads to the poll. Only the bootstrap processor gets `V_DISK`, so when the poll makes a process `READY` while another processor is idle, it sends that one `V_WAKE` (to all other processors) rather than leave the process for the idle processor's next tick. The boot log says `disk: completions by message-signalled interrupt` when this is on.
- A disk without the interrupt (the ATA drive, whose PIO transfer is over before the command is started, or a device whose MSI or MSI-X could not be set up) is polled instead: a processor with nothing to run while one of its commands is in flight looks again after a short spin.
- The kernel claims the local APIC's page as an `Mmio` block, turns the bootstrap processor's APIC on (keeping the 8259 on LINT0) and acknowledges `V_DISK` and `V_WAKE` itself. That claim is not exclusive: `boot/smp.c` uses the same page, before `main` and for the application processors' timer. Each processor's APIC is only ever touched by that processor, and Bastio touches it only with `Lock[Sys]` held and interrupts off, so the two never meet.
- Creating, removing, renaming, truncating and changing metadata still do their I/O synchronously. They first wait for the queue to empty, so the order on the disk stays the order of the calls.
- A command that fails, or runs for ten seconds, kills the disk: queued work is dropped, and every later file call on the disk fails. A write still waiting for its transaction then fails too (`EIO` for Linux programs), although its result had been decided at commit: the queue remembers the last transaction that finished before the disk died (`dq_kill`), and only those count as written.

#### Where the lock time went: byte-at-a-time copies

Before splitting the disk off `Lock[Sys]` (stage 4 of the plan), the time each system call holds the lock was measured: HPET readings around `finish` in `turn`, per call number, during one `diskbench` on NVMe (a temporary build, not kept). A file read held the lock for 840 µs per call and a 4 KiB write for 495 µs, against 8 µs for getpid. Almost all of it was copying. Every 4 KiB block was moved a byte (or a `get_u64`/`put_u64` of eight bytes) at a time: user memory to the transfer buffer, to the cache, to the device's page, and back. The kernel is compiled with `-mgeneral-regs-only`, so none of these loops is vectorised, and under TCG each iteration costs tens of host instructions.

Bastio now has bulk copies (`bcopy`, `bmove`, `frame_to_bytes`, `bytes_to_frame`, `dma_to_bytes`, `bytes_to_dma`; bastiolang `docs/language.md`), proved in bounds like `bget`/`bset` and compiled to `rep movsq`. The block paths use them: user memory (`src/space.bastio`), the cache (`src/diskq.bastio`, `src/diskfs.bastio`, whose `zero` now doubles a run of zeros with `bmove`), every DMA disk's data page, both network cards' buffers and the TCP and UDP queues, and the pipe and AF_UNIX rings. After that the lock is held for about 150 µs per file read and 170 µs per write.

Splitting the disk's state off (stage 4) would not change it, and stage 4 is not done. What would is calls that do not hold the one lock at all; see "How it scales".

The disk driver (`src/ata.bastio`) talks to the first drive of the legacy ATA controller in PIO mode with 28-bit sector numbers, polling with interrupts off; a 4 KiB block is one READ or WRITE SECTORS command for eight sectors. It owns the controller's ports 0x1F0 to 0x1F7 and 0x3F6 as `PortIo` capabilities claimed in `main`, so the proof checks that it touches no other port and that no other driver touches these. Every wait for the drive is bounded, so a missing or stuck drive makes an operation fail instead of hanging the kernel.

At boot the kernel installs the files in `files/` (built into the image with `include_bytes`). A process's descriptors are closed when it ends, and a file cannot be removed while a descriptor has it open.

### Waiting for the network

A Linux socket call with nothing to do yet (`read` or `recvfrom` with no data, `accept` with no connection, `write` on a TCP connection with a full send buffer) used to be restarted on every pass of the scheduler, so a process blocked in `accept` kept a processor busy. Now it sleeps in `SOCKWAIT` (`sock_retry` in `src/syscall.bastio`; `ps` says `socket`) and restarts once the card has received a frame or the clock has ticked since it went to sleep (`sock_wake`, after every system call and every device poll). AF_UNIX sockets are not on the card and still restart as before; so do the shell's native socket calls, which return at once and leave the waiting to the program.

Without more, a sleeper would wait for the next tick, since the card is only polled after an interrupt. So the card can interrupt too: the virtio card's receive queue raises MSI-X message 0, `V_NET`, aimed at the bootstrap processor (set up in `nic_new` before the card starts, as for the disks), and an e1000, which has no MSI, raises its PCI interrupt line, which the kernel unmasks at the 8259 unless the firmware routed it to the timer's, the keyboard's, the cascade's or COM1's. The boot log says `net: frames received by interrupt` when one is set up.

The interrupt is asked for only while some process sleeps in `SOCKWAIT` (`nic_listen` as one goes to sleep; `nic_quiet` once `sock_wake` finds none left). Each interrupt costs a trap and a poll under the lock, and with it on all the time, an echo through a busy-waiting program lost a third of its throughput to them. `nic_listen` polls the card once more after turning it on, for a frame that came in just before (a virtio card does not signal those).

Measured with `make netbench` (`test/netbench.sh`, `-smp 2`, QEMU's user-mode network, two runs per card under TCG, ticks at 100 Hz) on the same host, before and after (2026-10-10). | same, e1000 | 39-47 / 53-80 | 43-48 / 43-45 |

## User programs

A user program is ordinary Bastio built with `--target user`. `user/start.S` provides the image header and `_start`, which calls `main` and exits with its result. `user/user.ld` links it at `USER_BASE`, and the Makefile flattens it to a raw image in `build/user/*.bin` for the kernel to embed. The shell (`user/sh.bastio`) reads lines with `serial_read` (the `read` call), runs built-in commands, and starts the other programs with `sys_spawn` and `sys_wait`. Two programs are assembly on purpose: `fault.S` touches kernel memory to test fault isolation, and `straddle.S` passes buffers that cross page boundaries to test the kernel's copies.

Entering user mode is the one place where a value from the proved side controls the CPU directly. `bst_cpu_enter` therefore takes only `rip`, `rsp`, the general registers and the arithmetic flags from the saved context; the segments, IOPL 0 and the interrupt flag are forced, and non-canonical addresses are replaced. Whatever the kernel stores, user code runs in ring 3 with interrupts on.

## What is proved and what is trusted

Proved, for every input, by the Bastio compiler before any C is emitted:
- every page is owned by exactly one place at a time (the allocator, or one slot of one table), and the allocator's bitmap agrees with the pool;
- a table is empty when it is freed, so tearing down a process returns every page;
- table levels line up, frames go only into level-1 tables, slot 0 of a top-level table (the kernel's map) is never touched, and the table in CR3 is never freed;
- every buffer, string and vector index is in bounds, no arithmetic overflows, and the kernel's own `Buf`s, `Vec`s and tables are never leaked or used after being freed.

Trusted, and listed in the README's "What is trusted" table and in [trusted-base.md](trusted-base.md): `boot/`, `user/start.S` and the linker scripts, the bastiolang preludes, the compilers and Z3, and QEMU. What the proof does not cover: page contents (the kernel copies bytes, but the proof does not know what they mean), the hardware's behaviour, and termination (a kernel loop that never ends is not detected).

## Limits

These are current choices, not design limits; the README's "Status" lists them with the plan:
- one lock for the whole kernel state (the console's devices have their own); the kernel runs with interrupts off and polls the UART and the keyboard, console and PIT interrupts reach only the bootstrap processor, and an idle processor notices new work only at its next timer tick (no wake-up interrupts between processors);
- a 512 GiB user window per process (an 8 MiB stack at its top), at most `NPROC - 1` (255) processes;
- files are simple (32 in memory and 64 on disk, paths up to 255 bytes, files up to 64 MiB in memory and 1 GiB on disk, 8 descriptors per process; every write is copy-on-write, so a block written costs four block writes), and programs cannot be run from files yet;
- user pages are mapped writable and executable;
- the kernel's arena halts the machine when it runs out (the page pool does not: spawns fail cleanly).
