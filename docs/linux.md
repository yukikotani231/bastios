# Running Linux programs

BastiOS runs unmodified Linux x86-64 programs next to its own. This page says how it loads them and which system calls it implements, and how each behaves. [Getting started](getting-started.md), section 4, shows how to run one, and `make compat` (see [test/compat/README.md](../test/compat/README.md)) measures how much ordinary Linux userland works: a suite of checks, BusyBox applets, Lua, QuickJS, sqlite, tcc and GNU make, and the Bastio compiler with Z3.

## Loading programs

User programs are linked at `USER_BASE` (address 0) behind a small header (magic, memory size, entry), flattened to raw images, and embedded in the kernel with `include_bytes`.

The kernel also loads Linux x86-64 ELF executables: fixed-address executables whose segments lie in the user window, and PIEs, which it places at `PIE_AT` (0x400000). A non-PIE executable linked at the usual 0x400000, as Alpine's gcc is, loads where it asks, because the user address space holds none of the kernel. A dynamically linked PIE names its interpreter (`PT_INTERP`): the kernel loads that too, high in the window just below where `mmap` starts, and starts it with `AT_BASE` pointing at it; the interpreter then links the program. The interpreter is the file at that path, or, for musl's `/lib/ld-musl-x86_64.so.1` when there is no such file, a copy of musl's `libc.so` built into the kernel image, so programs linked only against musl's libc run as they come (other shared libraries would have to be files). It starts them with the stack the Linux ABI promises (argc, argv, envp and the auxiliary vector). Every header field is untrusted, and the proof shows each read stays inside the file and each copied byte lands in the window below the stack.

## System calls

Such programs make Linux system calls with the `syscall` instruction (`src/linux.bastio`): `read` (the console, blocking, a file or a pipe), `write` and `writev` (the console, a file or a pipe), `pipe`, `pipe2` (a pipe holds 64 KiB, and a write of up to `PIPE_BUF` bytes goes in whole), `mknod`/`mknodat` for named pipes, as `mkfifo` makes them (a writer's `open` waits for a reader; a FIFO is a file of the file system with the FIFO type bits, so it is listed, renamed and removed like a file and kept on the disk across reboots; up to four can be open at once), and for character and block device nodes (root only; the node keeps its device number as its contents and `stat` reports it in `st_rdev`; opening one gives the device its number names: 1:3 `/dev/null`, 1:5 `/dev/zero`, 1:8 and 1:9 the random devices, 5:0 and 5:1 the console, and `ENXIO` for any other) and socket nodes, `dup`, `dup2`, `dup3`, `fcntl` (duplicating, close-on-exec, record and open file description locks, leases, which are kept and reported but never broken, and a description's owner with `F_SETOWN`, `F_SETOWN_EX` and `F_SETSIG`: with `O_ASYNC` set, data arriving in a pipe or FIFO sends the owner SIGIO or the chosen signal, with the permissions of whoever set the owner; Who may reach another process this way is in [security.md](security.md). `inotify_init`, `inotify_init1`, `inotify_add_watch` and `inotify_rm_watch` (`src/lxinotify.bastio`) watch files and directories: reading the descriptor gives Linux's `struct inotify_event` records, in Linux's order (a directory hears of its entries' events, with their names, before the entry itself; renames tie `IN_MOVED_FROM` and `IN_MOVED_TO` with a cookie; equal events in a row are one; a full queue ends with `IN_Q_OVERFLOW`), and `poll` and `epoll` see it readable while events wait. Events come from the Linux system calls (not from BastiOS's own, nor from writes through shared mappings); there is no `IN_UNMOUNT`; `IN_DELETE_SELF` comes when the last name goes rather than when the last open descriptor closes, so an unlinked file still open reports only to watches on itself; there are at most 16 instances of 64 watches and 31 queued events each, as `/proc/sys/fs/inotify` says. `openat2` (`src/lxopen2.bastio`) checks `struct open_how` as Linux does (`EINVAL` for unknown flags, a mode without `O_CREAT`, or `O_PATH` with flags it does not take; `E2BIG` for a larger struct whose extra bytes are not zero) and honours all its resolve flags: `RESOLVE_IN_ROOT` makes the directory the root for the call, `RESOLVE_BENEATH` refuses absolute paths, `..` out of the directory and links leading out (`EXDEV`), `RESOLVE_NO_SYMLINKS` and `RESOLVE_NO_MAGICLINKS` refuse links (`ELOOP`), `RESOLVE_NO_XDEV` refuses entering `/proc`, `/sys`, `/dev` or a mount (`EXDEV`), and `RESOLVE_CACHED` is `EAGAIN` only with `O_CREAT`, `O_TRUNC` or `O_TMPFILE`. The checks look at the path once and the open resolves it again, so a rename in between can change what is opened, and `RESOLVE_BENEATH` lets an absolute link that stays inside through. Opening `/proc/PID/exe` opens the program, and `/proc/version` reads like Linux's. `name_to_handle_at` and `open_by_handle_at` (`src/lxhandle.bastio`) name a file or directory by its file layer handle, which survives renames; opening by handle needs `CAP_DAC_READ_SEARCH`. A handle has no generation number, so once its file is removed and the slot reused, the old handle opens the new file instead of failing with `ESTALE`; generated files such as `/proc` have handles only with `AT_HANDLE_FID`.

## Container runtimes

What `runc` (static, version 1.2) asks of the kernel beyond the namespaces and control groups above, so that `runc run` starts a container from an Alpine root and its process prints from inside it (`user/mcont.c` covers the pieces that need no runtime):

- `close_range` (closing, or `CLOSE_RANGE_CLOEXEC`), `PR_SET_CHILD_SUBREAPER` (a subreaper adopts the orphans below it, after a PID namespace's init), `PR_SET_KEEPCAPS` and `PR_CAP_AMBIENT` (recorded; capabilities still follow the user ids), and quiet `ENOSYS` for the keyring calls and the new mount API.
- `bpf` accepts only what a runtime does to a cgroup's device filter: `BPF_PROG_LOAD` of a `CGROUP_DEVICE` program, `BPF_PROG_ATTACH`, `BPF_PROG_DETACH`, `BPF_LINK_CREATE` and `BPF_PROG_QUERY` on a cgroup directory. The program is kept nowhere and nothing runs it, so the device rules are not enforced and a query finds nothing attached (`src/lxbpf.bastio`).
- `sched_getaffinity` names processor 0 only, although `/proc/cpuinfo` lists every processor and `nproc` therefore says 1: the scheduler does not pin a thread, and a mask that named more would make LTP's `getcpu01` (which pins to each processor and asks `getcpu`) fail.
- `syslog` (`klogctl`, which `dmesg` calls): the kernel keeps no log, so a read returns 0 bytes, `SIZE_BUFFER` says 16384, `SIZE_UNREAD` 0, and the other actions are accepted; all but `READ_ALL` and `SIZE_BUFFER` need root, a type above 10 is `EINVAL`, a read with no buffer is `EINVAL`, and the console level (type 8) must be 1 to 8. `dmesg` therefore prints nothing; the boot messages are on the console only.
- `/proc/stat` (`cpu` and `cpuN` lines in USER_HZ ticks: the time some process ran is counted as user time, the rest of the wall time as idle, split evenly over the processors; `intr` and `ctxt` are 0; `btime`, `processes`, `procs_running` and `procs_blocked`), `/proc/modules` and `/proc/diskstats` (both empty: there are no modules, and the disks keep no I/O counts) and `/proc/net/dev` (`lo` and `eth0` of the reader's network namespace; only the frame counts of `eth0` are kept, so bytes and errors read 0) are there, which is what BusyBox's `top`, `lsmod` and `ifconfig` read. `/proc/net/tcp` lists the connections of the reader's network namespace (state, addresses and ports; the queues, timers, owner and inode read 0, and IPv6 sockets, which run over the IPv4 stack, are listed here, with `/proc/net/tcp6` only a header), which is what BusyBox's `netstat -ant` reads. `/proc/net/udp` lists the UDP sockets of the reader's network namespace (local port and the datagrams waiting; the remote address, owner and inode read 0; `/proc/net/udp6` has only its header, as for TCP). `/proc/net/unix` lists the bound and listening unix sockets (type, listening flag and path, an abstract name with a leading `@`; the address, reference count and inode read 0, and the unnamed sockets of a connected pair are not listed). `/proc/net/raw` lists the raw ICMP sockets of the reader's network namespace (the protocol number in the port column, state 07, the datagrams waiting; the owner and inode read 0). `/proc/net/route` lists the default route and each interface's subnet in the reader's network namespace (destination, gateway, flags and mask; the metric, use and MTU read 0), which is what BusyBox's `route -n` and `netstat -rn` read. `/proc/net/arp` lists the card's ARP cache (address, MAC and the device; only in the namespace the machine boots in), which is what `arp -a` reads.
- `/proc/PID/task` lists the threads of the process (`task/TID` is a directory; the files under it are those of `/proc/TID`, so they describe the thread, not the process as Linux's per-thread `stat` would in a few fields).
- `/proc/PID/fd/N` is a link a path walk follows for a directory (a mount onto it, `chdir`, `openat2` below it), is reopened by `open` for a file (a new description, for a FIFO opened `O_PATH` as `exec.fifo` is), and is executed by `execve` (the cloned, sealed `memfd` copy of `runc`). `statfs` of `/proc` says `PROC_SUPER_MAGIC`, its root has inode 1, `/proc/PID/stat` gives a start time that is never 0, and `F_ADD_SEALS` and `F_GET_SEALS` work on a `memfd` (kept, not enforced).
- `tmpfs` mounts onto a directory of the disk file system (the container's `/dev`), `openat2` with `RESOLVE_IN_ROOT`, `RESOLVE_BENEATH` and `RESOLVE_NO_SYMLINKS` judged on the caller's logical paths, `MSG_PEEK | MSG_TRUNC` on a sequenced-packet socket (the size probe of runc's sync socket), `cgroup.freeze` (a frozen group's processes, and those of groups below it, are not scheduled until it is thawed; a process with a pending `SIGKILL` still runs so that it can end; `cgroup.events` shows `frozen 1`), and a descriptor on the old root that follows `pivot_root` so `fchdir` and `umount2(".", MNT_DETACH)` leave only the new root.
- Threads: a `tkill` or `tgkill` signal says `SI_TKILL` from the sender's group (glibc's `SIGSETXID` handler ignores anything else, which `setgid` in a threaded static program waits for); a thread group owns its children, so `wait4` and `waitid` from any thread collect them and every waiting thread wakes when one ends; SIGCHLD goes to the group's leader; a signal posted to a thread that does not hold the group's signal actions looks them up where they are; mount and other namespaces belong to a thread, and the working directory and root move between threads of a group only inside one mount namespace.

- Rootless: `runc --rootless` as an unprivileged user (`runc spec --rootless`) starts an Alpine root it owns in a user namespace that maps the user to 0. What it takes beyond the above: the user writes `uid_map` and `gid_map` for the child (the text may end in a NUL, as runc's length counts one); `setuid`-family calls look only at the arguments they take; the mapped root of a user namespace in a mount namespace of its own may `mount` (bind mounts, `tmpfs`, `proc`, `devpts`, `sysfs`, `mqueue`, `cgroup2`, overlay), `umount2` and `pivot_root` there, but not the machine's own mounts (a disk image, a tmpfs on a directory outside the namespace), and a tmpfs it mounts belongs to it; it holds the capabilities it has not dropped (`capget`, `capset`, `PR_CAPBSET_DROP`) in its namespace only; a pipe can be `fchown`ed by its owner to itself; the hard limit on descriptors starts at 4096 (the table still holds 256); `/dev/full` exists (a bind mount of it is how a rootless runtime makes the container's); and `/proc/self/fd/N` of a file under a namespace's tmpfs reads back as the name the process sees it by, which runc checks before it mounts onto it (`test/compat/progs/t_userns.c`, and a rootless container in `test/compat/alpine.txt`). Not done: the owner `/proc/PID` shows is the host's, not the namespace's (`ps` in a rootless container prints `nobody` for its own process), and `newuidmap` for more than one id.

Not done: enforcement of device rules.

## Overlay mounts

`mount -t overlay overlay -o lowerdir=A:B,upperdir=U,workdir=W DIR` (root's, and per mount namespace like a bind mount; `src/lxns.bastio`) merges directories of the file layer. A name is looked up in U, then A, then B, and the first layer that has it wins. A file named `.wh.NAME` in a layer hides `NAME` in the layers below it, and a `.wh..wh..opq` file hides everything below its directory. `getdents` lists the layers merged, once per name and without those marker files. Without `upperdir` the mount is read-only (`EROFS`). Writing goes to U: a file opened for writing, truncated, `chmod`ed, `chown`ed, given new times, or made the source of a rename or link is copied up first (contents, mode, owner and time; a directory only as an empty one, a symbolic link as a link), the directories above a new name are made in U from the layers that have them, and `unlink`, `rmdir` and `rename` of a name a lower layer has leave a `.wh.NAME` whiteout in U. A directory made again over a removed one keeps the whiteout beside it, which keeps the lower contents hidden.

Different from Linux: a whiteout is an empty regular file, not a character device 0:0, so a layer written by another overlay file system (Docker's `overlay2` directories) shows its whiteouts as files; there are no extended attributes, so opaque directories are marked by the `.wh..wh..opq` file; `workdir`, `index`, `redirect_dir` and the other options are accepted and ignored; renaming a directory that a lower layer has is `EXDEV` (as on Linux without `redirect_dir`); device, FIFO and socket nodes of a lower layer are not copied up (`EOPNOTSUPP`); a copy-up of a large file runs inside the system call, with the whole kernel locked; the layer paths of one mount take 255 bytes together; hard links between the layers are not kept. Files opened through the merge are the layer's own, so `st_dev` and the inode numbers are those of the layer the file lives in.

## ptrace

`ptrace` (`src/lxptrace.bastio`) lets a debugger watch and steer a process: `PTRACE_TRACEME`, `PTRACE_ATTACH` and `PTRACE_SEIZE`, `PTRACE_CONT`, `PTRACE_SYSCALL`, `PTRACE_SINGLESTEP`, `PTRACE_KILL` and `PTRACE_DETACH`, `PTRACE_PEEKTEXT`/`PEEKDATA`/`PEEKUSER` and `POKE...`, `PTRACE_GETREGS`/`SETREGS`, `GETREGSET`/`SETREGSET` of `NT_PRSTATUS`, `PTRACE_GETSIGINFO`/`SETSIGINFO` (the signal number only), `PTRACE_SETOPTIONS` and `PTRACE_GETEVENTMSG`. A traced process stops for each signal it takes and after `execve` (with `SIGTRAP`); the tracer sees the stop through `wait4` or `waitid` without asking for `WUNTRACED`, reads and writes its memory and registers, and resumes it with a signal or none. `int3` raises `SIGTRAP`. `PTRACE_SYSCALL` stops before and after each system call (with `orig_rax` the call and `rax` `-ENOSYS` before it; `PTRACE_O_TRACESYSGOOD` marks the stop with 0x80), except `getpid` and `gettid`, which a processor answers without the kernel lock; `PTRACE_SINGLESTEP` runs one instruction. `PTRACE_O_TRACEFORK`, `TRACEVFORK`, `TRACECLONE` and `TRACEEXEC` report their events: the tracee stops with `SIGTRAP` and the event in the wait status (`status >> 16`), `PTRACE_GETEVENTMSG` gives the new child's id, and a new child starts attached to the same tracer, stopped by `SIGSTOP`; a vfork parent hears of its event only when it runs again, and `waitid` does not carry the event. Not done: the exit event and `PTRACE_O_TRACEVFORKDONE` (those options are kept, and only `PTRACE_O_EXITKILL` acts), floating point and debug registers (the debug registers read as zero), and `PTRACE_INTERRUPT`. A tracer that is not the parent hears of its tracee's end once, and the parent reaps it.

## Network namespaces

`unshare(CLONE_NEWNET)` (with `CAP_SYS_ADMIN`) puts the caller in a new network namespace with only a loopback `lo`, down. `socket(AF_NETLINK, SOCK_RAW or SOCK_DGRAM, NETLINK_ROUTE)` speaks rtnetlink: `RTM_GETLINK`, `RTM_GETADDR` and `RTM_GETROUTE` dumps, and `RTM_NEWLINK`/`RTM_SETLINK`/`RTM_DELLINK` for veth pairs and bridges (made, deleted, set up or down, renamed, given a MAC, made a bridge's port with `IFLA_MASTER`, moved to another process's namespace with `IFLA_NET_NS_PID`). It also takes `RTM_NEWADDR`/`RTM_DELADDR` (one IPv4 address per interface) and `RTM_NEWROUTE`/`RTM_DELROUTE` (a namespace's default route). Changes need `CAP_NET_ADMIN`; anything else is `EOPNOTSUPP`. A veth's peer cannot be named in the request (BusyBox's `ip` cannot send one either): it is called `vethN`, and `ip link set vethN name NAME` renames it. Socket ioctls `SIOCGIFCONF`, `SIOCGIFFLAGS`, `SIOCSIFFLAGS`, `SIOCGIFINDEX`, `SIOCGIFNAME`, `SIOCSIFNAME`, `SIOCGIFADDR`, `SIOCGIFNETMASK`, `SIOCGIFBRDADDR`, `SIOCGIFHWADDR` (the hardware address; lo reads ARPHRD_LOOPBACK and zeros), `SIOCGIFMTU` and `SIOCGIFTXQLEN` see the caller's namespace. `socket(AF_INET, SOCK_RAW, IPPROTO_ICMP)` (with `CAP_NET_RAW`) sends ICMP messages in an IP header the kernel writes and receives every ICMP packet for its namespace, header included. Namespace 0 forwards and masquerades for the others; there is no netfilter, `setns`, `/proc/PID/ns/net` or `IFLA_NET_NS_FD`. See "Network namespaces" in [architecture.md](architecture.md).
