# Running Linux programs

BastiOS runs unmodified Linux x86-64 programs next to its own. This page says how it loads them and which system calls it implements, and how each behaves. [Getting started](getting-started.md), section 4, shows how to run one, and `make compat` (see [test/compat/README.md](../test/compat/README.md)) measures how much ordinary Linux userland works: a suite of checks, BusyBox applets, Lua, QuickJS, sqlite, tcc and GNU make, and the Bastio compiler with Z3.

## Loading programs

User programs are linked at `USER_BASE` (address 0) behind a small header (magic, memory size, entry), flattened to raw images, and embedded in the kernel with `include_bytes`.

The kernel also loads Linux x86-64 ELF executables: fixed-address executables whose segments lie in the user window, and PIEs, which it places at `PIE_AT` (0x400000). A non-PIE executable linked at the usual 0x400000, as Alpine's gcc is, loads where it asks, because the user address space holds none of the kernel. A dynamically linked PIE names its interpreter (`PT_INTERP`): the kernel loads that too, high in the window just below where `mmap` starts, and starts it with `AT_BASE` pointing at it; the interpreter then links the program. The interpreter is the file at that path, or, for musl's `/lib/ld-musl-x86_64.so.1` when there is no such file, a copy of musl's `libc.so` built into the kernel image, so programs linked only against musl's libc run as they come (other shared libraries would have to be files). It starts them with the stack the Linux ABI promises (argc, argv, envp and the auxiliary vector). Every header field is untrusted, and the proof shows each read stays inside the file and each copied byte lands in the window below the stack.

descriptors are shared), `clone(CLONE_VM | CLONE_VFORK)` as `posix_spawn` makes it (the parent lends its address space to the child, and waits, until the child calls `execve` or ends), threads: `clone(CLONE_THREAD)` as `pthread_create` makes it (with `CLONE_SETTLS`, `CLONE_PARENT_SETTID`, `CLONE_CHILD_SETTID` and `CLONE_CHILD_CLEARTID`), `futex` (`WAIT`, `WAKE`, `REQUEUE`, `CMP_REQUEUE`, `WAKE_OP` (as musl's condition variables and Qt use it) and the bitset forms, with timeouts on the monotonic or, with `FUTEX_CLOCK_REALTIME`, the wall clock; within a process, and across processes for a futex in a `MAP_SHARED` page without `FUTEX_PRIVATE_FLAG`) and `set_tid_address`, so musl's mutexes, condition variables and joins work (`src/lxthread.bastio`; the threads of a process share its address space, descriptors, working directory and signal actions, and run on several processors at once (see "Threads on several processors" in [architecture.md](architecture.md)); `exit` from a thread ends that thread, `exit_group` the process), `execve` (built-in programs at `/bin/NAME`, a program from a file system reading its largest code segment's pages from the file when it first runs them (`src/lazy.bastio`; the kernel gives `EFAULT` for such a page passed to a system call before then), with `/bin/sh` being BusyBox's `ash` so `system` and `popen` get a POSIX shell, ELF files such as `/elfdemo` from memory or `disk/`, a dynamically linked program's interpreter (`PT_INTERP`) found as the program is, from the caller's root and through symbolic links, so glibc's `/lib64/ld-linux-x86-64.so.2` starts Debian's programs in a chroot (`test/compat/debian.txt`), and `/proc/PID/exe`, the program that process runs, which is how ash runs a script with no `#!` line; a file starting with `#!` runs the interpreter that line names, with the line's argument, if any, and the script's path before the rest of argv, as on Linux: `ENOEXEC` for a line naming no interpreter, `ENOENT` for a missing one; with argv and the environment, up to 8192 arguments, 1024 environment strings and 128 KiB of them, laid out at the top of the stack as Linux does; a program the kernel itself starts, such as the shell's `ash`, gets `PATH`, `HOME=/` and `TERM=vt100`), `wait4`, `waitid` (ended children only), `times`, `gettid`, `arch_prctl(ARCH_SET_FS)` (the thread pointer) and `ARCH_SET_GS`/`ARCH_GET_GS` (the base `%gs` addresses with, kept per process and thread, as WebAssembly's wasm2c "segue" in Firefox uses it), `set_tid_address`, `exit`, `exit_group`, `getpid` and `getppid`; `set_robust_list`, `rseq` and `clone3` fail with `-ENOSYS` quietly (glibc carries on without them, so static glibc programs such as Z3 run), as does `io_setup` (nginx falls back to other ways of doing I/O); `io_uring_setup`, `io_uring_enter` and `io_uring_register` (`src/lxuring.bastio`, `test/compat/progs/t_uring.c`): up to 256 entries in a ring (the completion ring has twice as many), at most 8 rings, mapped with `mmap` at liburing's three offsets (`IORING_FEAT_SINGLE_MMAP`). The rings live in a RAM file the kernel reads and writes itself, never through a pointer into the program, and the positions it relies on are its own copies, so a program that overwrites a ring head or an array index only harms its own requests. Requests are done inside `io_uring_enter`: `NOP`, `READ`, `WRITE`, `READV`, `WRITEV` and `FSYNC` on files (an offset of -1 uses the file's position), and any other operation, or a descriptor that is not a file, completes with an error. `io_uring_enter` never waits (nothing is in flight) and stops taking requests while the completion ring is full; `epoll_ctl` accepts a ring but `poll` never reports it ready, and `splice`, `readahead` and `sync_file_range` refuse it as they refuse any descriptor that is not a file; linked requests, fixed files and buffers, `SQPOLL`, `IOPOLL` and every `io_uring_register` opcode but the probe are not done; `ioctl` `FICLONE`, `FICLONERANGE` and `FIDEDUPERANGE` (`src/lxreflink.bastio`, `test/compat/progs/t_reflink.c`): a clone copies the bytes, so the two files then hold equal data that changes independently, but no space is shared; ranges must be 4096-byte aligned unless they end at the source's end, an overlap in one file is `EINVAL`, a destination opened `O_APPEND` or read-only is `EBADF`, and a deduplication compares up to 1 MiB per destination (`bytes_deduped` says how much) and reports `SAME` or `DIFFERS` without sharing anything; a file on another file system is not told apart (Linux says `EXDEV`); `O_DIRECT` is kept on a file description and shown by `F_GETFL`, but not enforced (no alignment checks); `membarrier`'s query answers that no command is supported, so liburcu (BIND's `dig` and `host`) keeps to its own barriers, and any other command is `EINVAL`; every other call prints a note on the console and returns `-ENOSYS`. Linux fds 0 to 2 are the console, a terminal that starts in canonical mode: the kernel echoes what is typed, handles Backspace, hands a read the line once Enter (or Ctrl-D) is pressed, and turns LF into CR LF on output. A program can change that with `tcsetattr`, as editors and REPLs do: with `ICANON` off a read gets each byte as it is typed (`VMIN` above 1 counts as 1; with `VMIN` 0 it waits at most `VTIME` tenths of a second, or not at all), and `ECHO`, `ISIG` (Ctrl-C sends SIGINT), `ICRNL`, `OPOST`/`ONLCR` and `IUTF8` are obeyed (`IUTF8` is on at the start, as on Linux's console: erase takes back a whole UTF-8 character, and its echo backs over as many columns as the character filled, two for East Asian wide ones, which Linux counts as one); the other settings are kept and reported but change nothing. Pseudo-terminals (`src/lxpty.bastio`) give programs the same line discipline between two descriptors: opening `/dev/ptmx` makes a pair (sixteen at a time) and returns its master end, `TIOCGPTN` and `TIOCSPTLCK` (`ptsname`, `unlockpt`) lead to the slave `/dev/pts/N`, and what the master writes is the slave's input, cooked as the settings say, while what the slave writes comes out of the master. Each pair keeps its own `termios`, window size (`TIOCSWINSZ` sends SIGWINCH to the foreground group), foreground group (`TIOCSPGRP`; Ctrl-C and Ctrl-\\ go to it) and session (`TIOCSCTTY`; `/dev/tty` opens the session's pty). Closing the last master sends SIGHUP to the session, after which slave reads find end of file and writes fail with `EIO`; a master read fails with `EIO` once every slave is closed. Dropbear's SSH server uses them for logins (`test/compat/ssh.txt`). `/dev/dsp` is the Open Sound System's playback device on an HD Audio card (`src/lxsnd.bastio`): it plays 48 kHz 16-bit stereo only, and the ioctls that set the rate, channels or format answer with that, as OSS allows; without a card it fails to open with `ENODEV` (see "Sound" in [architecture.md](architecture.md)). `/dev/input/mice` and `/dev/psaux` give the mouse's 3-byte packets (a PS/2 mouse's, or a USB mouse's turned into that form) (buttons with the sign bits, then x, then y, up positive), as Linux's mousedev does in its default mode: a read takes what is queued, waits when nothing is (or fails with `EAGAIN` if opened `O_NONBLOCK`; `fcntl` cannot change that later), and `poll` reports `POLLIN` when a packet is waiting. Bytes written are mouse commands, answered as mousedev answers them (0xFA, the id for 0xF2, the status for 0xE9, a reset for 0xFF; only the answer to a write's last byte is kept): the IntelliMouse sequence (sample rates 200, 100, 80) switches to ImPS/2, whose 4-byte packets carry the wheel (up negative), which programs such as gpm and X's mouse driver ask for, and the sequence 200, 200, 80 switches to ImExPS/2 (id 4), whose fourth byte holds the wheel in its low four bits (signed, up negative, at most 7 a packet) and the back and forward buttons in bits 4 and 5; a USB mouse's side and extra buttons and a PS/2 mouse that reports five buttons feed it. Unlike Linux, the mode belongs to the device rather than to each open file, and opening it goes back to plain PS/2. Without a mouse the open fails with `ENODEV`. `/dev/fb0` is the screen as Linux's fbdev gives it (`src/lxfb.bastio`): 32 bits a pixel in the mode the boot loader set, `FBIOGET_VSCREENINFO` and `FBIOGET_FSCREENINFO` for the geometry and channel positions, and `write` at the file position (moved by `lseek`; `EFBIG` past the end of the screen, `ENOSPC` at it) to store pixels; the requests that would change the mode, pan or blank are accepted and do nothing. While a description of it is open the text console is not drawn on the screen (it goes on filling its text and the serial line), and when the last one closes the console is drawn again, which also removes what the program left. Writes go through a ring the console pump empties, so a full ring makes `write` sleep. There is no `mmap` of it yet, and without a screen the open fails with `ENODEV`. Each process has 1024 descriptors (`src/lxfd.bastio`; more give `EMFILE`, and more than 4096 open file descriptions in all give `ENFILE`); each is the console or an open file description shared by `dup` and `fork`: a file in the file system below, one end of a pipe, a directory being listed, or a socket (`src/lxsock.bastio` and `src/lxtcp.bastio`, over the kernel's sockets in `src/net.bastio` and `src/tcp.bastio`). That is enough for C programs built against musl libc as static PIEs (`user/mhello.c`, `user/mtest.c`) to use `printf`, `malloc`, `fopen` and `fgets`, and for BusyBox's `ash`, built unmodified, to run as an interactive shell on the console and start other programs, with pipes and redirection. BusyBox's `ls`, `cat`, `wc`, `head`, `rm`, `cp`, `kill`, `sleep`, `mkdir`, `rmdir`, `pwd`, `mv`, `chmod`, `touch`, `stat`, `ln`, `readlink`, `mkfifo`, `mount`, `umount`, `truncate`, `chown`, `unshare`, `pivot_root`, `chroot`, `hostname`, `nsenter`, and for users `su`, `login`, `passwd`, `chpasswd`, `adduser`, `addgroup`, `deluser`, `delgroup`, `id` and `whoami` (see [security.md](security.md)) are built in too, and `/bin/NAME` for each of them starts the BusyBox binary, which picks the applet from `argv[0]`. Each process has its own x87/SSE state, saved in a page of its own whenever it stops running. `int 0x80` keeps the BastiOS ABI, the one in bastiolang's user prelude. Calls 0 to 10 have named builtins there; the file calls (11 to 24, listed in `src/syscall.bastio`) go through its generic `sys_call` / `sys_send` / `sys_recv`, which lend the kernel a byte buffer.

A `poll`, `select`, `epoll_wait`, `pause`, `rt_sigsuspend`, `nanosleep` or `clock_nanosleep` that has to wait sleeps until a network frame comes in, the clock ticks (every 10 ms) or a signal is posted, and then looks again (`wait_asleep` in `src/lxtime.bastio`). So readiness that comes from elsewhere, such as a pipe another process writes, is seen up to 10 ms late, and a timeout ends up to 10 ms late. These calls used to run again on every pass of the scheduler, which kept a processor busy for every waiting process: an idle nginx kept two busy, and a 16 MiB download from it went at 0.86 MB/s, against 7 MB/s now (QEMU TCG, two processors).

Calls newer kernels added, and some they replaced (`src/lxextra.bastio`, `src/lxpidfd.bastio`): `preadv2` and `pwritev2` (at an offset, or at -1 for the file offset; `RWF_HIPRI`, `RWF_DSYNC`, `RWF_SYNC` and `RWF_NOWAIT` are accepted and change nothing, `RWF_APPEND` and other flags are `EOPNOTSUPP`), the old `getdents` beside `getdents64` (both list `.` and `..` first, and `lseek` on a directory with `SEEK_SET` or `SEEK_CUR` moves through the listing, so `rewinddir`, `telldir` and `seekdir` work), `sysfs` and `ustat` (the four file system types `/proc/filesystems` names), `fchmodat2` (with `AT_SYMLINK_NOFOLLOW`, which fails with `EOPNOTSUPP` on a link as on Linux, and `AT_EMPTY_PATH`), `readahead` and `sync_file_range` (checked, then nothing to do: there is no read-ahead or write-back to start), `vhangup` (root only; there is no terminal to hang up), `execveat` (with `AT_EMPTY_PATH` to run an open file; `AT_SYMLINK_NOFOLLOW` on a link is `ELOOP`), `O_PATH` (a handle that only names a file: calls that would read, write or change it fail with `EBADF`), the process descriptors `pidfd_open`, `clone` and `clone3` with `CLONE_PIDFD` (a new process, not a thread; the number goes to `ptid` or `clone_args.pidfd`), `ioctl(PIDFD_GET_INFO)` (the ids, with `PIDFD_INFO_CREDS` the credentials as the caller sees them, and with `PIDFD_INFO_EXIT` the wait status of a process that has ended, as a zombie or reaped until its slot is taken again; a process outside the caller's PID namespace, or a reaped one when no status is asked for, is `ESRCH`; no control group id; `test/compat/progs/t_pidfdinfo.c`), `pidfd_send_signal` (with or without a siginfo), `pidfd_getfd`, `poll` on a pidfd (readable once the process has ended) and `waitid(P_PIDFD)`, and `kcmp`, `process_vm_readv` and `process_vm_writev` (a pidfd keeps naming its process after the slot is reused by another; `PIDFD_THREAD` is not there, and `kcmp` compares open file descriptions exactly but every other resource per thread group). Who may reach another process this way is in [security.md](security.md). `inotify_init`, `inotify_init1`, `inotify_add_watch` and `inotify_rm_watch` (`src/lxinotify.bastio`) watch files and directories: reading the descriptor gives Linux's `struct inotify_event` records, in Linux's order (a directory hears of its entries' events, with their names, before the entry itself; renames tie `IN_MOVED_FROM` and `IN_MOVED_TO` with a cookie; equal events in a row are one; a full queue ends with `IN_Q_OVERFLOW`), and `poll` and `epoll` see it readable while events wait. Events come from the Linux system calls (not from BastiOS's own, nor from writes through shared mappings); there is no `IN_UNMOUNT`; `IN_DELETE_SELF` comes when the last name goes rather than when the last open descriptor closes, so an unlinked file still open reports only to watches on itself; there are at most 16 instances of 64 watches and 31 queued events each, as `/proc/sys/fs/inotify` says (root may write those files; the number is kept and read back, the limits themselves do not move). `/proc/sys/kernel/pid_max` is the same (301 to 4194304; ids are still below 512), and a forked process gets the lowest free id except the one handed out last, so a child that just ended does not give its id to the next fork (while `pid_max` is set to something else than its default, forks number round and round instead, as Linux does). `/proc/sys/kernel/pid_max` is the same (301 to 4194304; ids are still below 512), and a forked process gets the next free id after the one handed out last, so one that just ended does not give its id to the next fork. `fanotify_init` and `fanotify_mark` (also `src/lxinotify.bastio`, root only, in the same table of instances) report access, modify, open, open for exec and close events with a descriptor of the file, read as 24-byte `fanotify_event_metadata` records: marks on files and directories (`FAN_EVENT_ON_CHILD`, `FAN_ONDIR`), and on a mount or file system (`FAN_MARK_MOUNT`, `FAN_MARK_FILESYSTEM`, which cover every file under the directory they were given, by its path), ignore masks (ended by a modification unless `FAN_MARK_IGNORED_SURV_MODIFY`), `FAN_MARK_FLUSH`, events of one process on one file merged into one, and `/proc/PID/fdinfo` listing the inode marks. Only the notification class is there: no permission events, no `FAN_REPORT_*` flags (so no create, delete, move or attribute events), no unlimited queue or marks (an instance has 15 marks and 31 queued events), no `FAN_OPEN_EXEC` events from `execve`, and the descriptor of an event is opened when the instance is read, so a file removed in between is `FAN_NOFD`. `openat2` (`src/lxopen2.bastio`) checks `struct open_how` as Linux does (`EINVAL` for unknown flags, a mode without `O_CREAT`, or `O_PATH` with flags it does not take; `E2BIG` for a larger struct whose extra bytes are not zero) and honours all its resolve flags: `RESOLVE_IN_ROOT` makes the directory the root for the call, `RESOLVE_BENEATH` refuses absolute paths, `..` out of the directory and links leading out (`EXDEV`), `RESOLVE_NO_SYMLINKS` and `RESOLVE_NO_MAGICLINKS` refuse links (`ELOOP`), `RESOLVE_NO_XDEV` refuses entering `/proc`, `/sys`, `/dev` or a mount (`EXDEV`; names go through the caller's mounts first, so the files of a container's own `/sys/fs/cgroup` are on one file system, as runc's cgroup reads need), and `RESOLVE_CACHED` is `EAGAIN` only with `O_CREAT`, `O_TRUNC` or `O_TMPFILE`. The checks look at the path once and the open resolves it again, so a rename in between can change what is opened, and `RESOLVE_BENEATH` lets an absolute link that stays inside through. Opening `/proc/PID/exe` opens the program, and `/proc/version` reads like Linux's. `name_to_handle_at` and `open_by_handle_at` (`src/lxhandle.bastio`) name a file or directory by its file layer handle, which survives renames; opening by handle needs `CAP_DAC_READ_SEARCH`. A handle has no generation number, so once its file is removed and the slot reused, the old handle opens the new file instead of failing with `ESTALE`; generated files such as `/proc` have handles only with `AT_HANDLE_FID`.

## Container runtimes

What `runc` (static, version 1.2) asks of the kernel beyond the namespaces and control groups above, so that `runc run` starts a container from an Alpine root and its process prints from inside it (`user/mcont.c` covers the pieces that need no runtime):

- `close_range` (closing, or `CLOSE_RANGE_CLOEXEC`), `PR_SET_CHILD_SUBREAPER` (a subreaper adopts the orphans below it, after a PID namespace's init), `PR_SET_KEEPCAPS` and `PR_CAP_AMBIENT` (recorded; capabilities still follow the user ids), and quiet `ENOSYS` for the keyring calls and the new mount API.
- `bpf` accepts only what a runtime does to a cgroup's device filter: `BPF_PROG_LOAD` of a `CGROUP_DEVICE` program, `BPF_PROG_ATTACH`, `BPF_PROG_DETACH`, `BPF_LINK_CREATE` and `BPF_PROG_QUERY` on a cgroup directory. The program is kept in a slot of the kernel's shared word area and checked when it is loaded (loads of the context words, register and immediate ALU operations, forward jumps, exit; anything else is `EINVAL`). Every open of a device and every `mknod` of a device node then runs the programs attached to the caller's cgroup and to the cgroups above it, and is `EPERM` unless each returns an odd number, with Linux's context (type, access, major, minor). A cgroup holds two programs (`BPF_F_ALLOW_MULTI`); a link detaches when its descriptor closes. `BPF_PROG_QUERY` lists the ids (slot + 1) of the programs attached to the cgroup itself, `BPF_PROG_GET_FD_BY_ID` opens one by id, and `BPF_OBJ_GET_INFO_BY_FD` gives its type and id, so a runtime can find the old program and replace it (`test/compat/progs/t_devcg.c`).
- `sched_getaffinity` names processor 0 only, although `/proc/cpuinfo` lists every processor and `nproc` therefore says 1: the scheduler does not pin a thread, and a mask that named more would make LTP's `getcpu01` (which pins to each processor and asks `getcpu`) fail.
- `syslog` (`klogctl`, which `dmesg` calls): the kernel keeps no log, so a read returns 0 bytes, `SIZE_BUFFER` says 16384, `SIZE_UNREAD` 0, and the other actions are accepted; all but `READ_ALL` and `SIZE_BUFFER` need root, a type above 10 is `EINVAL`, a read with no buffer is `EINVAL`, and the console level (type 8) must be 1 to 8. `dmesg` therefore prints nothing; the boot messages are on the console only.
- `/proc/stat` (`cpu` and `cpuN` lines in USER_HZ ticks: the time some process ran is counted as user time, the rest of the wall time as idle, split evenly over the processors; `intr` and `ctxt` are 0; `btime`, `processes`, `procs_running` and `procs_blocked`), `/proc/modules` and `/proc/diskstats` (`/proc/modules` is empty, there are no modules; `/proc/diskstats` has one line for the disk, `bastio0`, with the reads, writes and flushes the disk queue finished, the blocks beyond the first of a command as merges, and the 10 ms ticks the commands ran, in the format of Linux 5.5 and after two fields of our own: how many times a process was woken from a disk wait, and the milliseconds all such waits added up to) and `/proc/net/dev` (`lo` and `eth0` of the reader's network namespace; only the frame counts of `eth0` are kept, so bytes and errors read 0) are there, which is what BusyBox's `top`, `lsmod` and `ifconfig` read. `/proc/net/tcp` lists the connections of the reader's network namespace (state, addresses and ports; the queues, timers, owner and inode read 0, and IPv6 sockets, which run over the IPv4 stack, are listed here, with `/proc/net/tcp6` only a header), which is what BusyBox's `netstat -ant` reads. `/proc/net/udp` lists the UDP sockets of the reader's network namespace (local port and the datagrams waiting; the remote address, owner and inode read 0; `/proc/net/udp6` has only its header, as for TCP). `/proc/net/unix` lists the bound and listening unix sockets (type, listening flag and path, an abstract name with a leading `@`; the address, reference count and inode read 0, and the unnamed sockets of a connected pair are not listed). `/proc/net/raw` lists the raw ICMP sockets of the reader's network namespace (the protocol number in the port column, state 07, the datagrams waiting; the owner and inode read 0). `/proc/net/route` lists the default route and each interface's subnet in the reader's network namespace (destination, gateway, flags and mask; the metric, use and MTU read 0), which is what BusyBox's `route -n` and `netstat -rn` read. `/proc/net/arp` lists the card's ARP cache (address, MAC and the device; only in the namespace the machine boots in), which is what `arp -a` reads.
- `/proc/PID/task` lists the threads of the process (`task/TID` is a directory; the files under it are those of `/proc/TID`, so they describe the thread, not the process as Linux's per-thread `stat` would in a few fields).
- `/proc/PID/fd/N` is a link a path walk follows for a directory (a mount onto it, `chdir`, `openat2` below it), is reopened by `open` for a file (a new description, for a FIFO opened `O_PATH` as `exec.fifo` is), and is executed by `execve` (the cloned, sealed `memfd` copy of `runc`). `statfs` of `/proc` says `PROC_SUPER_MAGIC`, its root has inode 1, `/proc/PID/stat` gives a start time that is never 0, and `F_ADD_SEALS` and `F_GET_SEALS` work on a `memfd` (the write, shrink and grow seals are enforced: `write`, `pwrite`, `ftruncate`, `fallocate` and a writable shared `mmap` fail with `EPERM`; a `memfd` is made with mode 0777 so it can be executed, and an unlinked file reached through `/proc/PID/exe` or `/proc/PID/fd/N` can be opened again).
- `tmpfs` mounts onto a directory of the disk file system (the container's `/dev`), `openat2` with `RESOLVE_IN_ROOT`, `RESOLVE_BENEATH` and `RESOLVE_NO_SYMLINKS` judged on the caller's logical paths, `MSG_PEEK | MSG_TRUNC` on a sequenced-packet socket (the size probe of runc's sync socket), `cgroup.freeze` (a frozen group's processes, and those of groups below it, are not scheduled until it is thawed; a process with a pending `SIGKILL` still runs so that it can end; `cgroup.events` shows `frozen 1`), and a descriptor on the old root that follows `pivot_root` so `fchdir` and `umount2(".", MNT_DETACH)` leave only the new root.
- Threads: a `tkill` or `tgkill` signal says `SI_TKILL` from the sender's group (glibc's `SIGSETXID` handler ignores anything else, which `setgid` in a threaded static program waits for); a thread group owns its children, so `wait4` and `waitid` from any thread collect them and every waiting thread wakes when one ends; SIGCHLD goes to the group's leader; a signal posted to a thread that does not hold the group's signal actions looks them up where they are; mount and other namespaces belong to a thread, and the working directory and root move between threads of a group only inside one mount namespace.

- Rootless: `runc --rootless` as an unprivileged user (`runc spec --rootless`) starts an Alpine root it owns in a user namespace that maps the user to 0. What it takes beyond the above: the user writes `uid_map` and `gid_map` for the child (the text may end in a NUL, as runc's length counts one); `setuid`-family calls look only at the arguments they take; the mapped root of a user namespace in a mount namespace of its own may `mount` (bind mounts, `tmpfs`, `proc`, `devpts`, `sysfs`, `mqueue`, `cgroup2`, overlay), `umount2` and `pivot_root` there, but not the machine's own mounts (a disk image, a tmpfs on a directory outside the namespace), and a tmpfs it mounts belongs to it; it holds the capabilities it has not dropped (`capget`, `capset`, `PR_CAPBSET_DROP`) in its namespace only; a pipe can be `fchown`ed by its owner to itself; the hard limit on descriptors starts at 4096 (the table still holds 256); `/dev/full` exists (a bind mount of it is how a rootless runtime makes the container's); and `/proc/self/fd/N` of a file under a namespace's tmpfs reads back as the name the process sees it by, which runc checks before it mounts onto it (`test/compat/progs/t_userns.c`, and a rootless container in `test/compat/alpine.txt`). `/proc/PID`, the directories in it (`ns`, `fd`, `fdinfo`, `task`) and its files belong to the process's effective user and group, which `stat` shows as the reader's user namespace maps them (`ps` in a rootless container prints `root` for its own process, not `nobody`). Not done: `newuidmap` for more than one id.

`crun` (static, version 1.x) runs the same containers as `runc`, from the same bundles: its own hostname, PID 1, cgroup limits, a seccomp filter, a read-only root, an overlay root (`test/compat/alpine.txt`). What it needed beyond the above: `/proc/PID/cmdline` holds the real argument strings (its re-execution of a sealed copy of itself keeps them), `clone` accepts `CLONE_NEWNET`, `/proc/sys/kernel/cap_last_cap` exists, and an `O_PATH` open of a device node holds the node, so `chmod` and `chown` through `/proc/self/fd/N` reach it. It runs `umount2(".", MNT_DETACH)` after `pivot_root(".", ".")` until the call fails, so a second one finds `.` still in the old root's detached mount and fails with `EINVAL`: here it is refused when the mount at the process's root is not the old root `pivot_root` stacked there, which keeps the new root's own mount and the read-only flag crun remounted onto it (`test/compat/progs/t_rootro.c`). ## Overlay mounts

Mount propagation (`src/lxprop.bastio`, `src/lxns.bastio`): `mount(NULL, dir, NULL, MS_SHARED | MS_SLAVE | MS_PRIVATE | MS_UNBINDABLE [| MS_REC], NULL)` sets the type of a mount of the namespace (the namespace's root is a mount once it is set on `/`; a directory that is not a mount point is `EINVAL`), and `/proc/PID/mountinfo` says `shared:N`, `master:M` and `unbindable`. Mounts are private until set. A bind of a mount is a peer of it if it is shared and a slave of the same master if it is a slave (`EINVAL` for an unbindable one); `MS_BIND | MS_REC` brings the mounts below the source along (except unbindable ones), and a new mount namespace's copies stay in the peer groups of the originals. A mount or an unmount below a shared mount happens at the same place below each of its peers, in every namespace, and below the slaves of its group (transitively); a slave's own mounts stay where they are. That makes a Docker or Podman volume with `rshared` or `rslave` bind propagation work. A tmpfs mounted in a mount namespace other than the first is a mount of that namespace (so it propagates), not one of the machine's. What is left out: mounts of the machine itself (the first namespace's tmpfs and disk mounts, which every namespace sees anyway), `proc`, `sysfs` and the like as sources of propagation, `open_tree` clones of a shared mount, `pivot_root` and `MS_MOVE` as propagation events, and the `propagate_from` field.

`mount -t overlay overlay -o lowerdir=A:B,upperdir=U,workdir=W DIR` (root's, and per mount namespace like a bind mount; `src/lxns.bastio`) merges directories of the file layer. A name is looked up in U, then A, then B, and the first layer that has it wins. A file named `.wh.NAME` in a layer hides `NAME` in the layers below it, and a `.wh..wh..opq` file hides everything below its directory. `getdents` lists the layers merged, once per name and without those marker files. Without `upperdir` the mount is read-only (`EROFS`). Writing goes to U: a file opened for writing, truncated, `chmod`ed, `chown`ed, given new times, or made the source of a rename or link is copied up first (contents, mode, owner and time; a directory only as an empty one, a symbolic link as a link), the directories above a new name are made in U from the layers that have them, and `unlink`, `rmdir` and `rename` of a name a lower layer has leave a `.wh.NAME` whiteout in U. A directory made again over a removed one keeps the whiteout beside it, which keeps the lower contents hidden.

Different from Linux: a whiteout is an empty regular file, not a character device 0:0, so a layer written by another overlay file system (Docker's `overlay2` directories) shows its whiteouts as files; there are no extended attributes, so opaque directories are marked by the `.wh..wh..opq` file; `workdir`, `index`, `redirect_dir` and the other options are accepted and ignored; renaming a directory that a lower layer has is `EXDEV` (as on Linux without `redirect_dir`); device, FIFO and socket nodes of a lower layer are not copied up (`EOPNOTSUPP`); a copy-up of a large file runs inside the system call, with the whole kernel locked; the layer paths of one mount take 255 bytes together; hard links between the layers are not kept. Files opened through the merge are the layer's own, so `st_dev` and the inode numbers are those of the layer the file lives in.

## ptrace

`ptrace` (`src/lxptrace.bastio`) lets a debugger watch and steer a process: `PTRACE_TRACEME`, `PTRACE_ATTACH` and `PTRACE_SEIZE`, `PTRACE_CONT`, `PTRACE_SYSCALL`, `PTRACE_SINGLESTEP`, `PTRACE_KILL` and `PTRACE_DETACH`, `PTRACE_PEEKTEXT`/`PEEKDATA`/`PEEKUSER` and `POKE...`, `PTRACE_GETREGS`/`SETREGS`, `GETREGSET`/`SETREGSET` of `NT_PRSTATUS`, `PTRACE_GETSIGINFO`/`SETSIGINFO` (the signal number only), `PTRACE_SETOPTIONS`, `PTRACE_GETEVENTMSG` and `PTRACE_GET_SYSCALL_INFO` (entry, exit and `SECCOMP_RET_TRACE` stops, with the call's number (x8 on AArch64) and arguments, the result at an exit and the filter's data at a seccomp stop; anywhere else op 0 and the header). A traced process stops for each signal it takes and after `execve` (with `SIGTRAP`); the tracer sees the stop through `wait4` or `waitid` without asking for `WUNTRACED`, reads and writes its memory and registers, and resumes it with a signal or none. `int3` raises `SIGTRAP`. `PTRACE_SYSCALL` stops before and after each system call (with `orig_rax` the call and `rax` `-ENOSYS` before it; `PTRACE_O_TRACESYSGOOD` marks the stop with 0x80), except `getpid` and `gettid`, which a processor answers without the kernel lock; `PTRACE_SINGLESTEP` runs one instruction. `PTRACE_O_TRACEFORK`, `TRACEVFORK`, `TRACECLONE` and `TRACEEXEC` report their events: the tracee stops with `SIGTRAP` and the event in the wait status (`status >> 16`), `PTRACE_GETEVENTMSG` gives the new child's id, and a new child starts attached to the same tracer, stopped by `SIGSTOP`; a vfork parent hears of its event only when it runs again, and `waitid` does not carry the event. Not done: the exit event and `PTRACE_O_TRACEVFORKDONE` (those options are kept, and only `PTRACE_O_EXITKILL` acts), floating point and debug registers (the debug registers read as zero), and `PTRACE_INTERRUPT`. A tracer that is not the parent hears of its tracee's end once, and the parent reaps it.

## Network namespaces

The disk that BastiOS leaves alone (docs/real-hardware.md) is readable as block devices (`src/lxsd.bastio`): `/dev/sda` is the whole disk and `/dev/sda1` .. `/dev/sda15` the partitions of its GPT (entry order) or of an MBR's four primary slots (logical partitions in an extended one are not found). They are root's and group disk's (rw-rw----), major 8; `read`, `pread`, `lseek` (end of file from the size) and `BLKGETSIZE`, `BLKGETSIZE64`, `BLKSSZGET`, `BLKBSZGET`, `BLKROGET` work, and opening for writing is `EROFS`. Reads go straight to the drive a sector (or an aligned 4 KiB) at a time, with no cache. There is no `/sys/block/sda` or `/proc/partitions` yet, and a disk that BastiOS mounts, or a second disk, has no such device. `test/shell_test.sh` reads a GPT disk through both.

`mount -t vfat` (or `msdos`) reads a FAT16 or FAT32 image (`src/fat.bastio`) the way `mount -t ext4` reads ext4 (docs/design/ext4-readonly.md): the image, a file or a loop device, is copied into memory below an empty directory and the mount is read-only (remount read-write is `EROFS`). Long names, the read-only attribute (modes 0444/0555), times (UTC) and sub directories are shown, the volume label is not; FAT12, a bad boot sector, a FAT shorter than the volume or a chain that leaves it are `EINVAL`. With `dd if=/dev/sda1 of=img`, a USB stick's FAT partition can be read. Not done: writing, exFAT, FAT12, mounting a device directly.

Generic netlink (`NETLINK_GENERIC`, `src/genl.bastio`) has the controller family `nlctrl` (id 16): `CTRL_CMD_GETFAMILY` by `CTRL_ATTR_FAMILY_NAME` or `CTRL_ATTR_FAMILY_ID`, and as a dump. A message to any other family id is ENOENT. `t_genl` checks it. The family `wireguard` (`src/wgdev.bastio`) configures WireGuard devices made with `ip link add wg0 type wireguard`: `WG_CMD_SET_DEVICE` and `WG_CMD_GET_DEVICE` (a dump, as `wg show` asks) keep the private key (clamped; the public key is derived with X25519), listen port, firewall mark and up to 64 peers in all, each with public and pre-shared keys, an IPv4 endpoint, keep-alive and 8 IPv4 allowed IPs (IPv6 is EAFNOSUPPORT). Both need `CAP_NET_ADMIN`. A device with a key and a listen port answers handshakes (`src/wgproto.bastio`, core/wgnoise from bastiolang): a peer with a persistent keep-alive and an endpoint sends an initiation (148 bytes, mac1 set) at once and again every 5 s until answered; an initiation is answered only if its mac1 is made for the device's key, it opens, comes from a configured peer and carries a timestamp later than the last one taken (so a recorded one is not answered again); a response is taken only for an initiation that is out. The initiator then shows a last-handshake time. A packet routed to a WireGuard device (its own subnet, or an address in a peer's allowed IPs) is sealed with ChaCha20-Poly1305 and sent to the peer's endpoint; with no session it is dropped and a handshake is started. An incoming data packet is opened only with a live session's key, must be new in a 1024-packet replay window, and must come from an address in the sending peer's allowed IPs; the peer's endpoint follows the source of the latest authenticated packet. A responder shows a handshake time once its first packet arrives. The encrypted packet of a tunnel does not pass the netfilter output hook (the packet inside did) and is dropped if it would itself route into a WireGuard device. TCP over the device uses an MSS of 1380. A persistent keep-alive is sent when its interval has passed without a packet to the peer; the side that started a session renews it when it sends after 120 s; a session older than 180 s carries nothing in either direction and is wiped (a peer with a keep-alive then asks for a new handshake). A device that takes more than 8 initiations with a good mac1 in a second is busy for the next second: an initiation without the mac2 of the cookie it would give its sender is then answered with a cookie reply (type 3, 64 bytes: XChaCha20-Poly1305 of a cookie that is a keyed BLAKE2s of the sender's address and port under a secret that changes every two minutes, sealed with the initiation's mac1 as associated data) and costs no Diffie-Hellman work; a peer that gets a cookie reply for its initiation keeps the cookie for 110 s and sends the initiation again at once with the mac2. The same holds for responses: a busy initiator answers a response without a valid mac2 with a cookie reply, the responder keeps the cookie for the session it has not yet seen a packet under, and puts the mac2 on the responses it sends next. When a new session replaces the current one, the old one is kept as a receive-only previous session (its key, counter window and birth time) until it is 180 s old, so packets sent under the old keys just before the handshake finished are still taken, each counter once; a previous session never sends, never confirms and is erased with the peer or when the session ends. A responder that already has a confirmed session keeps sending under it when it answers a new initiation: the new keys are its next session, which only receives and becomes the current session (the old one becoming the previous one) when the first packet under it authenticates, so a lost response does not leave the responder sending under keys the initiator never got. A responder with no confirmed session takes the new keys as its current one at once. `t_wgnext` drops the first response and checks this. `t_wgprev` checks the previous session (a held packet taken once after a rekey, a replay of it refused, one released after 180 s refused). `t_wgcfg`, `t_wghs`, `t_wgtun` (two namespaces, a relay that duplicates and replays packets), `t_wgcookie` (a flood of initiations with a good mac1 and a garbage body, and a handshake that still gets through) and `t_wgtimer` (the timers, about six minutes of real time) check it.

AF_ALG (`src/lxalg.bastio`) offers the hash algorithms `sha256`, `sha384`, `sha512`, `sha1`, `md5`, `hmac(sha256)`, `hmac(sha384)`, `hmac(sha1)` and `hmac(md5)`: `socket(AF_ALG, SOCK_SEQPACKET, 0)`, `bind` of a `struct sockaddr_alg` with type `hash`, `setsockopt(SOL_ALG, ALG_SET_KEY)` for an hmac, `accept`, then `send`/`sendmsg` (`MSG_MORE` for pieces) and `read` of the digest. The kernel copies the message in at `send` and the digest out at `read`, so it never hashes memory of the program or of a file, and changing a buffer after it was sent changes nothing. At most 16 AF_ALG sockets (the bound socket and each accepted one count), 8 KiB of message each; a longer send is `EMSGSIZE`. AEADs (type `aead`: `gcm(aes)` with a 16- or 32-byte key and `rfc7539(chacha20,poly1305)`, 16-byte tag, 12-byte IV) take their `ALG_SET_OP`, `ALG_SET_IV` and `ALG_SET_AEAD_ASSOCLEN` control messages in `sendmsg`; `read` returns the associated data again followed by the ciphertext and tag (or the text), only if the buffer holds all of it, and a wrong tag is `EBADMSG` with no text given. Symmetric ciphers (type `skcipher`: `ctr(aes)`, `cbc(aes)` and `ecb(aes)` with a 16-, 24- or 32-byte key, and `xts(aes)` with a 32-, 48- or 64-byte key, which is two AES keys) take `ALG_SET_OP` and a 16-byte `ALG_SET_IV` in `sendmsg` (`ecb(aes)` takes no IV: a zero-length one is accepted, any other length is `EINVAL`, and none is needed) and are read as a whole (a buffer that is too small, or a CBC, ECB or XTS message that is not whole 16-byte blocks (XTS needs at least one and has no ciphertext stealing; Linux leaves a working value in the XTS IV afterwards, so a program sends a fresh one with each request, and this kernel keeps the IV as it was), is `EINVAL` with no output). The operation and IV stay on the socket and the IV moves on with each operation (the last ciphertext block for CBC, the counter after the blocks used for CTR), so successive messages continue one chain as in Linux. The input is a copy made at send and the result a copy made at read, so nothing is encrypted or decrypted in place in a program's memory. `sendfile` and `splice` (from a pipe) into an accepted socket add the bytes to the message like `send`: they are copied into the socket's own buffer, so a file's pages are never the cipher's input or output and are never written to (decrypting from a file leaves the file as the ciphertext), and changing the file afterwards changes nothing. Not done: splice out of the socket. `t_alg` and `t_algskc` check it.

IPsec: a `NETLINK_XFRM` socket (`src/xfrm.bastio`) adds, replaces, reads (one, or as a dump), deletes and flushes the security associations of ESP, as `ip xfrm state` does: `XFRM_MSG_NEWSA`, `DELSA`, `GETSA`, `FLUSHSA`. An association is ESP over IPv4 in transport or tunnel mode, keyed by destination, SPI and network namespace (at most 64 in all), and the only algorithm is `XFRMA_ALG_AEAD` `rfc4106(gcm(aes))` with a 128-bit tag and a 128- or 256-bit key plus the 4-byte salt. Other algorithms are `EOPNOTSUPP` or `ENOENT`, AH is `EPROTONOSUPPORT`, and everything needs `CAP_NET_ADMIN` in the namespace, reads too (a key is secret). Policies are kept the same way: `XFRM_MSG_NEWPOLICY`, `UPDPOLICY`, `DELPOLICY` (by selector and direction, or by index), `GETPOLICY` (one or a dump) and `FLUSHPOLICY`, at most 32 in all. A policy has an IPv4 selector (source and destination network, protocol), a direction (in or out), an action (allow or block) and at most one ESP template; ports, an interface, the forward direction and chains of templates are `EOPNOTSUPP`, so no policy is kept that would match more than it was asked to. The packet path is there too. A packet the stack sends that an out policy covers is wrapped in ESP (RFC 4303 with RFC 4106's GCM: the nonce is the salt and the 8-byte IV, which is the sequence number, and the associated data are the SPI and the sequence number) and sent to the association's far end: from the packet's own source in transport mode, from the association's source in tunnel mode. A block policy drops, and so does a missing association, a used-up sequence space, or a packet that would not fit one frame (nothing is fragmented). An ESP packet for this machine is looked up by destination, SPI and namespace, checked against the replay window (a window of 0 counts as 1: the check is never off), and opened into a buffer of its own: the received packet is never written to. Only an authenticated packet moves the window, and the padding must be 1, 2, 3 ...; the packet inside then goes round the loopback queue as if it had arrived again, if the in policy that covers it allows it and names the association's reqid and mode. A tunnel-mode packet needs such a policy (the addresses inside a tunnel are authenticated by nothing else), and its source may not be a loopback, multicast or reserved address. A packet that comes in plain is dropped when an in policy asks for ESP. A raw socket of protocol ESP (`CAP_NET_RAW`) can send ESP packets, which is how `t_esp` seals packets by hand with `AF_ALG` and replays, changes and cuts them. An association keeps its `xfrm_lifetime_cfg` and reports it, with the `xfrm_lifetime_cur` counters (bytes and packets carried, when it was added and first used), in `GETSA`. The hard limits are enforced: an association that has carried its packet or byte limit, or that is older than its add-seconds or first-use-seconds limit, is deleted (its key erased) before the next packet or request looks for it, so it neither seals nor opens another packet, and `GETSA` then says `ESRCH`. Only authenticated packets count, so forged ones cannot use up a limit. The soft limits are stored and reported but stop nothing, and there is no `XFRM_MSG_EXPIRE` notification (there are no netlink multicast groups for XFRM). A limit of 0, which a zeroed `xfrm_lifetime_cfg` holds, is treated as none, as is ~0. The times are in seconds on the stack's own clock, not wall-clock time. Not done yet: soft-limit notification, IPv6, fragmentation and path-MTU feedback (a datagram that does not fit once wrapped is lost), and forwarding. Extended sequence numbers work: an association made with `XFRM_STATE_ESN` and `XFRMA_REPLAY_ESN_VAL` (its `replay_window` field must be 0, the window comes from the ESN state, at most 255 packets are kept, and the bitmap it carries is not read) counts in 64 bits, puts the low half in the ESP header, seals with the 12-byte associated data of RFC 4106 (SPI, high half, low half) and uses the whole number as the IV so a nonce is never reused. A receiver infers the high half from the highest number it has taken (RFC 4303, appendix A.2.2) and opens the packet under it, so a packet sealed under any other high half, or with the 8-byte data of a 32-bit association, fails to open and does not move the window; the replay check works on the 64-bit number across the 2^32 wrap. `GETSA` reports the counters (not the bitmap) in `XFRMA_REPLAY_ESN_VAL`. An ESN flag without the attribute is `EINVAL`. ESP in UDP (RFC 3948, NAT traversal) works with `XFRMA_ENCAP` of type `UDP_ENCAP_ESPINUDP` (other types are `EOPNOTSUPP`, ports of 0 `EINVAL`; `GETSA` reports it back): the ESP packet goes out behind a UDP header from the encap source port to the encap destination port (no UDP checksum), and a UDP datagram to the source port of any association of the namespace that has one is taken as ESP in UDP: a one-byte `0xff` keep-alive is dropped, a datagram that starts with four zero bytes (IKE) is left for a socket, and anything else is looked up like ESP. Unlike Linux, no socket with `UDP_ENCAP` has to be bound to the port: an association made by `CAP_NET_ADMIN` is enough. An association with encapsulation takes only ESP in UDP and one without takes only plain ESP; the in policy of the packet inside applies, not the one for the outer UDP datagram. The original-address field and checksum fix-ups for transport mode behind a NAT are not done. `t_xfrm`, `t_esp`, `t_xfrmlife`, `t_esn` and `t_espudp` check it. A socket that binds with, or joins by `NETLINK_ADD_MEMBERSHIP`, multicast group 2 (`XFRMNLGRP_EXPIRE`, needs `CAP_NET_ADMIN`) receives `XFRM_MSG_EXPIRE` when an association passes its soft limit and again, with `hard` set, when it is removed at its hard limit. Group 4 (`XFRMNLGRP_SA`) hears `XFRM_MSG_NEWSA` when an association is added or replaced and `XFRM_MSG_DELSA` (its id) when one is deleted, flushed or expires. Other netlink families accept the groups but nothing is sent to them yet.
