# BastiOS on AArch64

BastiOS builds for AArch64 and boots on QEMU's `virt` machine. This is the first stage of the port tracked in [bastiolang#119](https://github.com/yukikotani231/bastiolang/issues/119) and [#194](https://github.com/yukikotani231/bastios/issues/194): a kernel with the processor and platform parts done, running the native-ABI programs on the same process table, scheduler state, system calls and file system as x86-64. The Linux layer, the network and more than one processor and more than one processor came stage by stage (see "What is not there yet").

```sh
sudo apt-get install z3 qemu-system-arm gcc-aarch64-linux-gnu   # on an x86-64 host
make ARCH=aarch64          # build/aarch64/bastios.bin (a Linux arm64 Image: QEMU, U-Boot and UEFI pass it the device tree)
make ARCH=aarch64 run      # boot it on this terminal (Ctrl-A X quits)
make ARCH=aarch64 test     # boot it and drive the shell (test/aarch64_test.sh)
```

The build proves `src/aarch64/main.bastio` and the shared kernel modules it imports (`src/proc.bastio`, `src/syscall.bastio`, `src/fs.bastio` and the rest, each choosing its device-specific parts from `src/aarch64/arch` through `--lib src/aarch64`) with bastioc1's `--target kernel --arch aarch64`, translates it to C, and compiles it with `aarch64-linux-gnu-gcc` (plain `gcc` on an AArch64 machine). `make ARCH=aarch64` and `make` share `build/bastioc1`, the proof cache and `BASTIOC0`, `BASTIOLIB`.

## What runs

`make ARCH=aarch64 run` boots to the BastiOS shell. The native programs work: `hello`, `spin`, `true` and `sh` itself, which starts programs, waits for them, lists (`ps`) and kills them, reads the console and powers off (`halt`, through PSCI `SYSTEM_OFF`). The timer interrupt preempts a program that never makes a system call (`spin &`), and at power off every page is back in the pool.

`src/aarch64/main.bastio` is the scheduler every processor runs (`sched`, under one kernel lock, as on x86-64: `smp_run`) over the shared `Kernel` (`src/kernel.bastio`); the architecture parts are in `src/aarch64/arch`: the register layout (`regs.bastio`: 37 saved words, 16 of them past the usual process row), the program images, the files the file system starts with, the block layer (a virtio-mmio disk, else a loop device in memory), the network card (virtio-mmio) and an empty sound card. The device window starts at 0 here (`src/aarch64/arch/mmiowin.bastio`). The kernel reads the device tree the platform copied at boot (`boot_info` query 10, byte by byte; `src/aarch64/dt.bastio` walks it in Bastio, every offset checked against the tree's own size), takes the row of `virtio,mmio` nodes it lists (QEMU virt: 32 slots from `0x0a000000`, 512 bytes apart; the same row if there is no tree) and claims the slots one at a time; a slot is kept only if it holds the wanted device. The drivers, the virtqueue code and the slot scan are the ones x86-64 uses on Firecracker (`src/virtio_blk.bastio`, `src/virtio_net.bastio`, `src/virtio_mmio.bastio`); only the transport layer (`src/<arch>/arch/vt.bastio`) differs, because AArch64 has no I/O ports. The clock follows the 100 Hz timer. The file system lives in memory, with the disk's files under `disk/` (`echo text > disk/file` survives a reboot).

The processes are set up as on x86-64: an address space of four-level translation tables (the shared code builds them), the image at `USER_BASE` (address 0; a PIE goes to `PIE_AT`, 0x400000), the stack at the top of the 512 GiB user window, system calls with `svc #0` (number in x8, arguments in x0-x2), results in x0. Programs are built with `--target user --arch aarch64` and the image header of `user/start-aarch64.S`.

## User code on its own table

User code runs on a translation table of its own with none of the kernel's memory in it, as on x86-64 (`src/aarch64/arch/userbase.bastio`): the window is seen from address 0, so a non-PIE executable (Linux links one at 0x400000) loads where it was linked, and a null pointer faults. TTBR0 holds the kernel's identity map whenever Bastio code runs. The compiler's AArch64 prelude sees the platform define `bst_platform_deferred_ttbr0` and, instead of loading a process's table, records it in word 3 of `bst_platform_mmu_state`; `bst_cpu_enter` fills the processor's shadow table (`bst_shadow_root`, whose slot 0 is the window's level-3 table, slot 1 of the process's own), then jumps into the trampoline page, which TTBR1 maps at `0xffff000000000000` and which holds the exception vectors. The trampoline loads the shadow table into TTBR0 just before the `eret`; every exception from EL0 loads the kernel's table first, parking the user's x0 in `TPIDRRO_EL0` while it does. Neither flushes the TLB: user translations are tagged with an 8-bit ASID in TTBR0 (255 numbers, handed out per table by `bst_user_ttbr` in `platform.c`; the kernel's own translations are not global and carry ASID 0). A processor flushes its TLB on the way to user mode only if entries were taken out of some table since its last flush (the compiled kernel counts them and passes the count in word 1 of `bst_platform_mmu_state`). When the numbers run out they roll over: every TLB is flushed (broadcast) and the numbers some processor is running under stay with their tables, so two tables never share one. A table's number is dropped when its page is given back (`bst_platform_table_free`), so the next table on that page does not inherit it. `test/aarch64_test.sh` forks more than 255 address spaces to cross a rollover.

## More than one processor

The platform starts the other processors once, before the kernel runs: it lists the `cpu` nodes of the device tree, and for each one other than the boot processor asks PSCI (`CPU_ON`, through `hvc`) to start it at `bst_secondary_entry`, which turns the MMU on with the kernel's tables, finds the processor's own redistributor by its affinity and parks in a `wfe` loop with its timer off. `smp_run` hands every parked processor `sched` (the compiler's `bst_platform_smp_start`/`join`); each then ticks at 100 Hz on its own and runs processes taken out under the kernel lock, holding a lease on the process's address space while it runs. The boot processor's tick is vector 32 and counts the kernel's time; another processor's is 48 and only charges the process that ran. `TPIDR_EL1` points at a processor's block (`struct pcpu`: its saved user context, the interrupt that ended its last wait, its number); each has a 64 KiB stack. `test/aarch64_test.sh` runs with `-smp 4` (`SMP=n` changes it) and checks the banner, `cpus`, and that three spinning programs are running at once. Idle processors sleep until their own tick (no inter-processor interrupt yet), and the address-space leases are not parked across system calls as on x86-64.

## Linux arm64 programs

An AArch64 ELF executable (`user/lxhello-aarch64.c` is `mhello`, `user/lxtest-aarch64.c` is `mtest`, a static glibc program) runs under the same Linux layer as on x86-64. A process loaded from an ELF file carries the Linux ABI flag (`F_ABI`): its `svc #0` is a Linux call with the number in x8 and the arguments in x0-x5. `src/aarch64/lxnum.bastio` turns the asm-generic numbers into the Linux layer's own (those with the same meaning on x86-64; the rest answer ENOSYS). What differs between the two ABIs is taken from `src/<arch>/arch`: register names and the call-number word (`regs.bastio`), struct stat and statx (`statfmt.bastio`), the signal frame (`sigframe.bastio`; arm64 has no restorer in sigaction, so the return trampoline sits in the vDSO page, which is also a small shared object, `user/vdso-aarch64.c`, whose `__kernel_clock_gettime` reads the virtual counter in user mode with the kernel's own arithmetic: `boot.S` sets `CNTKCTL_EL1.EL0VCTEN`; the wall clock and the CPU-time clocks stay system calls), the sigaction layout, clone's tls/ctid order, `struct epoll_event` (16 bytes here, packed 12 on x86-64) and uname's machine. `test/aarch64_test.sh` runs both programs. musl-linked programs, BusyBox's `ash` (the same source and applet list as x86-64's, built as a static non-PIE glibc executable at 0x400000, `arch/aarch64/Makefile`) is the `ash` command of the native shell: arithmetic, pipes between forked applets and files work (`test/aarch64_test.sh`), and Ubuntu's arm64 `busybox-static` runs too, tried by hand. `make ARCH=aarch64 compat` runs the Linux compatibility suite (`test/compat`) on it: the suite's C programs (all but t_ptrace, which reads x86-64 registers) as static glibc executables, and a BusyBox with the suite's applet list, then Alpine (apk in a chroot; dynamically linked musl programs), Debian (glibc's dynamic linker) and Node (V8's JIT) from the arm64 layers of the same Docker Hub images as the x86-64 suite's; it fails if a check in `test/compat/baseline-aarch64.txt` stops passing. The Alpine, Debian and Node groups need the kernel to leave AT_SYSINFO_EHDR out while the vDSO page holds no ELF image (musl's dynamic linker would read it as one), and EL0 access to CTR_EL0 and cache maintenance by address (`SCTLR_EL1.UCT`, `UCI`) for V8's code flushes. The checks that fail are written for x86-64 (the int 0x80 door, a seccomp filter with x86-64 call numbers) or for musl (glibc's `sigprocmask` reads the set before the kernel does).

## The platform

The platform is the trusted base besides the compiler's AArch64 preludes ([trusted-base.md](trusted-base.md)):

| File | What it does |
| --- | --- |
| `boot/aarch64/boot.S` | The Linux arm64 Image header; entry at EL1 with the device tree in x0 (also where a started processor enters, `bst_secondary_entry`); the trampoline page (the exception vectors and the TTBR0 switch); enabling the MMU; `bst_cpu_enter` (the `eret` to EL0 and the register save on the way back) |
| `boot/aarch64/efi.c` | The UEFI application entry: moves the image to its link address, finds the device tree, exits the boot services, turns the MMU off and jumps in |
| `boot/aarch64/platform.c` | Reading the memory map from the device tree; the kernel's translation table (1 GiB blocks: normal memory where RAM fills the gigabyte, devices in the first 4 GiB where there is none, a table of 2 MiB blocks where the two share one); the GICv3 (each processor's redistributor) or GICv2 (the CPU interface) that the device tree names, and the generic timer (100 ticks a second); acknowledging interrupts; `bst_cpu_wait` (`wfi`); starting the other processors with PSCI and parking them |
| `boot/aarch64/linker.ld` | The trampoline page's own section, load address (`0x40080000`, where QEMU puts a kernel) and `_end`, where the page pool starts |

The kernel starts at EL1 or EL2 (firmware such as U-Boot and UEFI usually hands over at EL2): `boot.S` drops from EL2 to EL1 with the setup EL2 owes it (AArch64 EL1, the counter and timer open to EL1, no FP trap, the GIC system registers enabled). The PSCI conduit (`hvc` or `smc`) is the one the device tree's `psci` node names. `test/aarch64_test.sh` runs both (`VIRT=,virtualization=on` starts QEMU at EL2).

The image is also a PE/COFF application (the header in `boot.S`, as Linux's `Image` is), so a UEFI firmware can boot it from a FAT partition as `EFI/BOOT/BOOTAA64.EFI`. `boot/aarch64/efi.c` is what a boot loader does: it asks for the memory at the kernel's link address, copies the image there, finds the device tree in the firmware's configuration table, leaves the boot services, turns the MMU and caches off and enters the image with the tree's address in `x0`. It needs RAM free at `0x40080000`. A firmware that publishes no device tree but ACPI tables (QEMU's with the default `acpi=on`, a server's) is handled too: `efi.c` writes a small tree from the XSDT's tables — the MADT (processors with their MPIDRs, the GIC's distributor and redistributors or CPU interface), the FADT (whether PSCI is called with `hvc` or `smc`), SPCR (a PL011 console) and MCFG (the PCI Express window) — and RAM from the firmware's memory map, so the kernel reads one kind of description whatever the firmware is. virtio-mmio slots and the clock, which ACPI describes only in AML, fall back to QEMU virt's defaults and to none. `ACPI=1` keeps ACPI on in `test/aarch64_test.sh`; only the tables above are read, there is no AML interpreter. `UEFI=/usr/share/qemu-efi-aarch64/QEMU_EFI.fd test/aarch64_test.sh` boots through the firmware (Debian/Ubuntu: `qemu-efi-aarch64`), at EL1 and, with `VIRT=,virtualization=on`, at EL2.

PCI Express: the host bridge's configuration window (the device tree's `pci-host-ecam-generic` node) is how the kernel reaches configuration space (`src/aarch64/arch/pcicfg.bastio`; x86-64 uses the I/O ports behind the same `src/pci.bastio`). A machine started with `-kernel` has no firmware to give the devices their BARs, so `pci_assign` does: every memory BAR of a bus-0 endpoint that is zero or lies beyond the device window (what EDK2 does with a 64-bit BAR) gets an address in QEMU virt's 32-bit window. Interrupts from PCI devices are not routed yet, so the drivers poll. An NVMe drive is the disk when there is one (`NVME=1 test/aarch64_test.sh`); the kernel's map holds the gigabyte of the configuration window when it lies above 4 GiB (QEMU's default). An Intel e1000-family card on the bus (QEMU `e1000`, `e1000e`, `igb`; `src/e1000.bastio`, shared with x86-64) is the network card when the machine has no virtio-mmio one (`NIC=e1000 test/aarch64_test.sh`); it is polled. A modern virtio PCI function (`disable-legacy=on` on QEMU) is the disk or the network card too: `src/aarch64/arch/vpci.bastio` reads the function's vendor capabilities (common, notification and device configuration, which must lie in one memory BAR), and `Vt` gets a PCI flavour of the same transport (`VIRTIO_PCI=1 test/aarch64_test.sh`); also polled. A USB stick with a BastiOS partition behind an xHCI controller on the bus is the disk when there is no NVMe drive (`src/xhci.bastio`, shared with x86-64; `USB=1 test/aarch64_test.sh` builds one with `tools/mkusb.py --blank`); its commands are polled, and the keyboard and mouse on the controller are not used yet (the console is the UART).

The interrupt controller and its addresses come from the device tree (`arm,gic-v3`, or `arm,cortex-a15-gic` / `arm,gic-400` for a GICv2), with QEMU `virt`'s GICv3 as the fallback; `test/aarch64_test.sh` runs against both (`GIC=2` for `-M virt,gic-version=2`). The console is the first `arm,pl011` node (`bst_uart_base`), and the virtio-mmio window comes from the tree too.

## What is not there yet

Tracked in [#194](https://github.com/yukikotani231/bastios/issues/194) and its siblings:

- musl, BusyBox and the compat suite on arm64, ptrace register sets ([#196](https://github.com/yukikotani231/bastios/issues/196));
- the interrupt controller and the UART from the device tree too (the platform still uses QEMU virt's addresses for them), the other drivers, and the clock from the generic timer's counter instead of the tick count;
- inter-processor interrupts to wake an idle processor, and parked address-space leases ([#195](https://github.com/yukikotani231/bastios/issues/195));
- real hardware ([#197](https://github.com/yukikotani231/bastios/issues/197)).
